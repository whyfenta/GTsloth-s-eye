# GTsloth-s-eye · 樹懶的工作

首頁是「樹懶的工作」視覺主目錄，共六個功能位置：「樹懶的盤點」、「樹懶的管理」與四個準備中的保留位置。一般桌面採三欄兩列、手機採兩欄三列；在正常字級與一般螢幕高度下可一頁看完，較小視窗或放大字級時允許捲動以保持可讀性。

盤點工具獨立網址：https://whyfenta.github.io/GTsloth-s-eye/inventory/ ，可直接加入書籤；點盤點頁左上角品牌或手機版「主目錄」即可返回首頁。管理工具網址：https://whyfenta.github.io/GTsloth-s-eye/management/ 。首頁不載入盤點、管理、PDF 或 OCR 模組。

公開網址：https://whyfenta.github.io/GTsloth-s-eye/ （GitHub Pages，main CI 通過後自動部署最新版）。舊版 Sites 網址 https://gtsloth-inventory.b93403003.chatgpt.site/ 停在 v1.1.2，僅能經 Codex 手動發布。GitHub 公開儲存庫 `whyfenta/GTsloth-s-eye` 是唯一修訂來源；Sites 保留獨立發布來源庫。

繁體中文的瀏覽器庫存 OCR 與 A4 條碼盤點表。使用 Vite、TypeScript、PDF.js、Tesseract.js、pdf-lib 與 JsBarcode。

## 使用

1. 選擇或拖放一份或多份 PDF、JPG、PNG，可分次加入、逐份移除；合計最多 200 頁、200 MiB，同一檔案不會重複加入。加入時只檢查格式、頁數與解析度，不會開始辨識；全部加入後按「開始辨識」。辨識完成後再加入或移除檔案，會先詢問並清除目前結果。庫存簡表可在樺穎的 IM1C1 依自訂條件設定簡表範圍後，將印表機設定為「列印至 PDF」產生。
2. 等候逐頁辨識；暫停會完成目前頁才停下。取消會終止 OCR Worker，之後可按「重新開始辨識」。多份檔案時先讀每份的第一頁，比對表頭上方的門市名稱：全部相同才繼續讀其餘頁面；兩份由 PDF 文字直接讀到的名稱不同即停止，須移除不同門市的檔案再重新開始；名稱讀不到，或含掃描辨識結果而不一致時，列出各份的名稱請人工確認是否同一門市，確認後才繼續。每份檔案各自判斷方向與欄位位置，不沿用其他檔案，因此每份的第一頁都要有表頭。
3. 校對代號、名稱、儲位及帳量。預設「只看有疑義」會彙整所有頁面的待確認列；點「對照」可看原始列與原名稱，名稱前綴可在對話框修改。沒有疑義時會明確顯示可直接產生盤點表。
4. 有疑義的列已標色並在名稱下列出原因（只是說明已依格式移除前綴的提示不標色）；需要勘誤時直接修正欄位，代號或帳量辨識不一致時點選原圖旁的候選值。確認全部疑義後，勾選最終確認會一併放行其餘無疑義品項；確認後再修改任一欄，該列會回到待確認。可關閉「只看有疑義」逐頁瀏覽，← → 手動換頁，欄位中按 Enter 移到下一列。儲位空白是一般值，不列為疑義。辨識到帳量為 `0` 的安全列不會進入校對或輸出；負數保留。多份檔案的資料合併：不同檔案中同代號、同儲位且帳量相同的列視為重複，只保留一筆（保留較清楚的辨識；已確認的列不會被取代），頁面選單與統計顯示刪除筆數；帳量不同時兩筆都保留，標為須逐筆確認的疑義，改成一致後輸出只印一筆。同一檔案內的列一律不合併。所有來源頁必須通過格式檢查，全部疑義須確認，才能輸出。
5. 選擇六編碼或儲位排序、22.6 / 25.8 / 29 mm 最低列高，下載 PDF。無論哪種排序，帳量為負數的品項都先排在最前，之後才是正數品項，方便優先處理。印表機使用 A4 直式、100% 原尺寸。

範本是掃描文件，中文藥名、包裝字形、儲位「三／二／四」與千分位容易誤辨；OCR 結果不是校對後資料。保留劑量、劑型及末尾 `(管3)` / `(管4)`，不以藥品字典猜測替換。

## 樹懶的管理（安全量、呆藥、空位清單）

1. 「庫存簡表」與「醫品調劑數量統計表」各有一個匯入區：庫存簡表可加入多份 PDF、分次補頁；醫品調劑數量統計表一次只匯入一份，要更換時先移除原檔；合計最多 400 頁（含零庫存列印的庫存簡表可達約 150 頁，加上調劑表仍可一次匯入；盤點工具維持 200 頁）、200 MiB，以 SHA-256 判斷同一檔案不重複加入。**只接受系統列印、沒有圖片的文字 PDF**；掃描檔、圖片檔或含隱藏 OCR 文字層的頁面一律拒收，本功能不做 OCR。按「開始解析」後先讀每份檔案第一頁核對報表種類與門市，再讀其餘頁面。放錯區的報表會說明應放的位置並停止。
2. 每頁都須印有表頭、門市與原報表頁次（庫存簡表 `頁次 n of total`，調劑表 `頁次：n/total`），調劑表另須有統計期間與給付方式。各頁的門市、期間、給付方式、總頁數與列印日期須一致，不同期間或篩選條件不會混算。庫存簡表的補頁檔可從原報表第 2 頁開始；缺頁、同頁碼內容不同會阻擋計算；完全相同的重複頁只計一次。同一報表中同碼的多筆調劑明細是合法資料，一律加總。
3. 門市以「門市編號＋店名」識別：調劑表「營業點：0026 26永和福和店」與庫存簡表「26北-永和福和店」視為同店；庫別不單獨作為門市依據。門市編號不同即拒絕，人工確認也不能覆蓋；只有無法自動判斷時才請人確認。庫存列印日早於調劑截止日只提示，不拒收。任一份報表的列印日期距今已達 7 天（一週）以上時，來源核對與產生清單處都會顯示警語，三份 PDF 的說明開頭也會印上「【警語】…輸出結果可能失真」，提醒重新列印最新報表。
4. 調劑表的文字儲存順序與版面不同，依座標分欄：代號與名稱依起點、右對齊的次數與數量依終點；健保價從不讀取。庫存簡表沿用盤點的文字層解析，取庫存量不取寄庫量。代號以字串保存。非六碼列（如 `R001`）保存為排除紀錄、不計入 N，修正代號後可「恢復此列」；缺代號但有數值的列、負數、缺單位、同碼不同單位、同碼同儲位重複等須修正或附理由排除，不能一般勾選放行。可對照原報表該列的影像。名稱沿用盤點的前綴清理，**只有本功能保留「缺貨」與「冷藏」**（`缺貨 PENTOP…`、`冷藏 Delta Pen…`；兩者皆有時一律印成 `缺貨冷藏 …`），其後的 `C-`、包裝等照常清除。
5. 產生安全量清單前可選擇三張策略卡，預設為**平衡派**：

   | 策略 | 係數（高頻 → 低頻） | 主要優勢 | 主要需求 |
   | --- | --- | --- | --- |
   | 倉鼠派 | 3.5～1.2 | 供貨不穩定時仍有充足貨源 | 較大的調劑與儲存空間 |
   | 平衡派 | 2.5～0.8 | 較寬的係數梯度保留高頻用藥，從較低頻用藥節省空間 | 兼顧備貨餘裕與儲存空間 |
   | 羚羊派 | 1.2～0.6 | 精控備貨量以配合固定倉儲空間 | 更密切、頻繁地關注貨源 |

   計算使用精確分數，最後才進位：統計月數依日曆月，區間為 `[起日, 截日+1日)`，以起日日號為每月錨點（月末截到該月最後一天），餘天除以該錨點月段的天數；2026/06/16～2026/10/15 為 4 個月。`A = 合計次數 ÷ 月數`、`B = 四捨五入(合計數量 ÷ 合計次數)`、月用量 `A × B`；係數依品項在本門市清單內的 A 排名決定（第 i 名，0 起算，`p = 1 − i / (K − 1)`，同 A 同名次）：前 1/3（`p ≥ 2/3`）採策略最高係數，其餘為 `最低係數 + (最高係數 − 最低係數) × p ÷ (2/3)`，末位採最低係數，僅一筆時採最高係數；品名保有「缺貨」前綴的品項（以清單印出的名稱判斷）係數再 +1；保有「冷藏」前綴的品項，因冷藏空間固定、不容超量，係數（含缺貨加成後）再 × 0.8；兩者只影響建議安全量，不改變入選與排名；建議安全量 `ceil(A × B × 係數)`。倉鼠派保持原曲線（其餘名次為 `1.2 + 3.45 × p`）；係數代表要備幾個月的用量。N 為不同的有效六碼數；`K = min(floor(N × 10%), A > 8 的品項數)`，依 A 降冪、同值依六碼，不擴增 K，N < 10 時可為 0 筆。切換策略會即時更新安全量預覽，品項篩選、合作診所判定及呆藥／空位規則維持一致；同一頁重新解析或更換檔案會保留策略選擇。
6. 安全量清單 PDF 標題為「安全量調整及採購建議清單」，欄位依序為六編碼、品名、現有庫存量、調劑頻率(/月)（A）、均月銷（A × B）、建議安全量、待採量；`待採量 = 建議安全量 − 現有庫存量`，庫存已足夠時記 0，簡表無此碼時印「—」。現有庫存量**大於 4 倍均月銷**（4 個月用量，恰為 4 倍不標示）時以紅色粗體印出（預覽同樣標示）：開立處方的醫院若指定換藥造成用量銳減，這些藥的逾期耗損風險較高。清單每碼一列，庫存量為同碼各儲位合計、名稱取庫存簡表第一筆。調劑有碼而庫存簡表沒有的品項會全部列出，不補 0、不從 N 移除；其中落在安全量清單內的須逐一核對並勾選確認，清單的現有庫存量欄印「簡表無此碼」，名稱改用調劑表名稱（可能被截短）。
   **合作診所供貨的門市**：先依一般規則排出安全量清單；其中**本店無庫存**的六碼（庫存簡表沒有任何列，或各儲位庫存合計為 0）**超過 10 個**時，判定此門市有合作診所供應部分貨源（10 個以下仍視為本店品項：沒有列的照上述方式逐一確認，庫存 0 的照印 0）。庫存合計為 0 與「簡表無此碼」意義相同，因為含零庫存列印的簡表會列出整個商品檔（0015 的清單 171 筆中有 96 筆庫存為 0）；判定後，這些無庫存的六碼，以及庫存不足 0.1 個月用量（約 3 天，含負庫存；15 南崁店 45 筆、占清單用量 40%，26 永和為 0；使用者可在來源核對區勾選放寬為 0.2 個月，約 6 天，讓更多品項遞補，但本店庫存偏低、確需採購的品項也可能一併被略過，畫面與 PDF 會註明此風險；預設仍為 0.1，重新匯入檔案會回到預設）的六碼，視為主要由合作診所供應，不由本店監控安全量：安全量清單略過它們，由 A 排序的後一位向前遞補，N 與 `floor(N × 10%)` 不變，K 仍不超過「A > 8 且本店有庫存」的品項數；沒有列的六碼仍列在缺碼清單供查閱，但不需勾選確認。來源核對區與清單 PDF 表頭／頁尾會註明判定依據、略過與遞補筆數。
7. 呆藥（庫存量 ≠ 0）與空位（庫存量 = 0）取不在調劑表有效六碼集合中的庫存列，保留各儲位、依盤點的儲位排序（空白在後）；負庫存照列並標「負庫存異常」。兩份清單只在統計期間**嚴格大於 2.5 個月**、給付方式為「全部」、且使用者確認庫存範圍涵蓋要評估的儲位時開放；庫存簡表沒有任何零庫存列時，空位清單另需使用者確認列印時已包含零庫存，否則不開放。
8. 三份 A4 直式 PDF 可各自勾選、預覽、下載；名稱換行、整列不跨頁，每頁重複清單標題、門市、統計期間、欄名、來源檔名、校對版本、程式版本與頁碼；安全量清單標題附策略名稱與係數範圍、下載檔名附策略名稱；頁尾只印「紅色粗體為現有庫存量 > 4 倍均月銷：醫院換藥致用量銳減時易逾期耗損。」一句（另有警語時一併印出），公式不在 PDF 重複，省下的頁尾行數讓表格多容納列數；無資料時印出說明頁。任何來源、校對、確認、策略或勾選變更都會使已產生的 PDF 失效。
9. **校對回饋**：按「產生 PDF」成功後，若這次校對有名稱修正、欄位修改、提示後未修改即確認的列或手動排除，會自動把校對紀錄送到開發者的回饋試算表（同一份校對只送一次；送出失敗不影響清單，下次產生時再試）。內容為六碼、原始品名、程式提示、名稱／代號／單位／儲位的修改前後、排除理由、所選策略與遮罩、門市編號與程式版本；次數、數量、庫存量**只記欄位名稱、不記數值**，**不送出報表檔案、店名與統計期間**。產生按鈕旁會說明送出的內容。未設定回饋網址時不送出、也不顯示說明。

以倉鼠派搭配 2026/10 的兩份範本實測：調劑表 28 頁、1,108 筆有效明細（另 `R001` 1 筆排除）、1,069 個六碼，A > 8 有 175 項，K = 106；`000206` 兩筆合計 C = 165、Q = 4,287，A = 41.25、B = 26、A×B = 1,072.5、係數 3.5、建議安全量 3,754，庫存 1,990（儲位 5脂41@）。庫存簡表 29 頁 1,002 列全為正庫存（沒有零庫存列，所以空位清單需另行確認）；197 個調劑六碼不在這份庫存簡表，其中 `123863`、`159262` 兩個在安全量清單內（未超過 10 個，不是合作診所供貨，須逐一確認）。確認後安全量清單 106 筆 4 頁、呆藥清單 130 筆 5 頁。

0015 桃園南崁店調劑表（2026/06/01～2026/09/30，54 頁）：2,142 筆明細（`R001`、`R003`、`R004` 排除）、N = 1,719 個六碼、4 個月，A > 8 共 587 項，前 10% = 171 筆。搭配含零庫存的 0015-09全 庫存簡表（154 頁）時判定為合作診所供貨：無庫存者，以及庫存不足 0.1 個月用量者（如 `174686` 每月約 4,409 次、庫存 -9）略過並由後一位遞補。

私有範本的回歸測試：`MANAGEMENT_USAGE_PDF=… MANAGEMENT_INVENTORY_PDF=… npm test`（先核對兩檔 SHA-256；可加 `MANAGEMENT_OUTPUT_DIR` 保存三份 PDF 供目視檢查）。未提供時明確跳過。

## 資料與隱私

- 沒有檔案上傳 API、庫存資料庫、分析追蹤、外部 OCR 服務、LocalStorage、IndexedDB 或 Service Worker。
- 例外：樹懶的管理產生 PDF 時，會把校對修改紀錄（見上方「校對回饋」）送到 `src/feedback-config.ts` 設定的 Google Apps Script 網址；報表檔案、店名、統計期間與任何數量都不送出。
- 使用者檔案、原圖裁切與結果只存在當次頁面記憶體。圖片檔只在辨識或檢視原圖時解碼，加入多張照片不會同時佔用解碼後的記憶體。清除／關閉／重新整理會失去資料；下載 PDF 由使用者裝置保存。
- OCR 模型、Worker、WASM、PDF.js 字型資源及中文字型均從網站本身載入。HTTP 快取可能保存公開依賴資源，不保存庫存文件。
- 原始庫存 PDF、人工基準 JSON、測試影像、輸出及詳細辨識紀錄留在本機，Git 忽略這些資料，部署封包只有靜態程式與公開依賴資源。

## 校對回饋試算表（設定一次）

1. 在 Google 雲端硬碟建立一份試算表（例如「樹懶的管理 校對回饋」），選單「擴充功能 → Apps Script」，把 `docs/feedback-apps-script.gs` 的內容整份貼上並儲存。
2. 「部署 → 新增部署作業」，類型選「網頁應用程式」；執行身分選「我」，存取權選「所有人」。授權後複製結尾為 `/exec` 的網址。
3. 把網址填入 `src/feedback-config.ts` 的 `FEEDBACK_ENDPOINT`，依一般流程發布。網址是公開的接收位址，不是密碼；接收端只接受本程式的格式、限制大小與筆數，並把以 `=`、`+`、`-`、`@` 開頭的文字轉成純文字，避免被當成公式。
4. 試算表會自動建立「送出紀錄」（每次一列：時間、版本、門市編號、策略、各類筆數）與「明細」（每筆名稱修正、欄位修改、未修改即確認、手動排除一列）。定期以「類型」篩選「明細」：同樣的名稱修正反覆出現代表清理規則要補；同一種提示常被原樣確認代表提示可能是誤報；排除理由重複出現代表可改為自動判斷。
5. 之後若修改接收端程式，須在 Apps Script「管理部署作業」更新同一個部署的版本，網址才會維持不變。

## 格式判斷與擷取

**來源自動分流（逐頁）**：系統直接列印的 PDF（如 Bullzip 等虛擬印表機）帶有真正的文字層，會直接讀取文字，代號、名稱、儲位與帳量不經 OCR，也不載入辨識模型；橫向列印的頁面會自動轉正，表格以小計／頁尾行為結束。頁面只要含有任何圖片（掃描檔，包括掃描器附加的隱藏 OCR 文字）或讀不到表頭，就改用下方的 OCR 流程。手動指定方向重試一律使用 OCR。文字頁在頁面選單標示「PDF 文字」。

**掃描檔的數字辨識**：掃描 PDF 直接取出內嵌原圖，以原解析度辨識（不放大，最長邊上限 4000 px），避免重新渲染再縮放。表頭整行被自動分段漏掉時，會再以稀疏文字模式找表頭字。每列的代號與庫存量另外逐格裁切、放大並黑白化，以三種方式重讀（同一欄的格子疊成一張圖，每種方式只辨識一次），連同兩次整欄辨識共五票投票：三票以上一致且沒有第二個候選有兩票，就自動採用；否則採用最多票的值並列出候選，標為「多次辨識不一致」，須逐筆確認。逐格辨識不允許小數點，避免千分位逗號誤讀成小數點。沒有名稱也沒有庫存量的短數字（如「庫別: 0026」）不會成為商品列。名稱與儲位的辨識分數只在低分時有意義（實測兩份掃描 83 筆：名稱低於 60 分 36 筆中 35 筆確實有誤），因此只有名稱低於 60、儲位低於 40 才提示「辨識品質差」並將欄位標色；其餘仍需逐列確認。

**解析度確認**：匯入掃描檔時會估算解析度（PDF 依內嵌圖片與頁面尺寸計算；JPG/PNG 以整張 A4 估算），低於 300 dpi 會先說明錯誤率較高並詢問是否繼續；取消則不開始辨識。系統列印的 PDF 不檢查。

依「商品代號、名稱、國際條碼、儲位、庫存量」五個表頭的相對位置與六位商品列判斷，店名不是表格辨識條件，只用於輸出標題與多份檔案的同門市確認（比對時忽略空白、全半形與日期時間）。表頭 OCR 有缺字時，會對同一表頭列重做窄帶辨識，依序嘗試單行、區塊與稀疏文字模式。各次辨識分開保留，再取有效表頭；重試不會覆蓋先前辨識正確的欄名。所有必要表頭仍須存在、由左至右排列並位於同一列。續頁可沿用已接受頁面的欄位位置，但仍需符合列結構與報表／前綴特徵；混入其他報表會阻擋輸出。

代號以字串保留前導零，不合併同碼不同儲位。帳量取庫存量，不取寄庫量。文字層會依原始 text run 分欄，避免把同一個 run 截成相鄰欄位；OCR 對帳量採用最後一個足夠寬的字距分開欄位，絕不跨空白拼接數字。兩種頁面分割／數字字元設定互相比對；不一致、缺值、低信心、疑似千分位與前綴疑義均提示人工確認。名稱只從開頭逐段清除已知狀態（停供、不售、換包、冷藏、避光、近效、缺貨、自費、客訂、追禁售、公費、限店等）、`C-` 標記與其短標籤（如 `(紅)`、`(贈藥)`，後接 `&` 亦可辨識）及包裝規格；名稱尾端另移除完整的 `-高健保`、`-高價藥` 標記（`(管4)-高價藥-診所用` 留下 `(管4)-診所用`），其他尾綴不動。包裝／內包裝可含全半形單或雙斜線，單位另涵蓋封、捆、聯、徘；狀態後的連字號、`C-` 後的 `&` 與標籤後的 `&` 均視為前綴語法。`C-` 被 OCR 讀成 `(-`、`-` 等且後接包裝或標籤時依格式移除並提示確認，`C-` 前未知的中文狀態字移除並提示確認；殘留的中文加 `A-`／`B-`／`C-` 標記會留在安全網中提示確認，沒有狀態字的單獨 `C-` 保留並標為疑義。與中文相鄰的 OCR 空白會移除，英文字詞與數字之間的空白保留。第一次代號辨識漏讀的列會由第二次辨識補回並標示，同列出現多個代號或庫存量會標為疑似合併。

來源保留頁碼、欄位座標、原名稱與信心。末筆商品已辨識出的連續跨行名稱會接回同筆，帳量維持原欄位範圍，並排除頁尾／總計文字。校對畫面只建立選中頁的商品列。後續頁與不同方向頁可透過原圖檢視及方向重試；若首張完全無法辨識，應改用較清楚的來源重新匯入。

## 印刷

A4 210 × 297 mm、留白 10 mm；五欄寬 40 / 60 / 22 / 25 / 43 mm。表格區由距下緣 264 mm 至 15 mm（249 mm），預設 22.6 mm 列高每頁 11 列（25.8 mm 為 9 列、29 mm 為 8 列；名稱換行增高的列會減少該頁列數）；標題頂端距上緣約 10 mm、頁尾基線距下緣 8 mm，仍避開一般印表機 3–5 mm 的不可列印邊界。Code 128C 含開始碼、校驗碼、停止碼，六位資料共 68 模組；X = 0.4 mm、線高 10 mm，置中後左右留白各 6.4 mm（16X）。為保留條碼高度與 16 pt 六位代碼，範本的各垂直留白縮小 20%：預設列高 22.6 mm、條碼黑線間距 12.6 mm；列頂至條碼 2.4 mm、條碼至代碼約 1.0 mm、代碼至列線約 2.2 mm，下一列條碼前再留 2.4 mm。代碼底部至下一列條碼約 4.6 mm；選擇較高列高時，下方留白隨之增加。

原代號另印於條碼下，使用 16 pt Courier。實量欄 43 mm 完全留白，可手寫九位數。名稱 16 pt、帳量以 Courier-Bold 20 pt（數字過長放不下時才縮小到剛好放入，不拆行）、儲位 10 pt；負數帳量的品項一律排在正數之前（表頭註明負數筆數），兩組各自依所選規則排序；依儲位排序時，儲位空白的品項在各組內排在最後；名稱依字詞換行（不拆開 `3ML`、`(管4)` 等單位與短括號），可增加列高，整筆不跨頁。第二、四等交錯列從名稱欄延伸至實量欄套淡綠網底，條碼欄維持白底。每頁重複門市、欄名與頁碼；表頭另印來源檔名（多份時為第一份檔名與檔案數）、筆數、刪除重複筆數與校對版本，對應產生當下凍結的校對資料，資料或設定一改，舊 PDF 即失效無法下載。

網頁預覽以正確編碼後的 Libre Barcode 128 字型顯示；PDF 使用同一 Code 128C 編碼的向量線條。PDF 內完整嵌入靜態 Noto Sans TC 400 字型（fontkit 子集化 CJK 時文字層正常但字形顯示空白，已於 2026-10-10 以靜態字型重測確認），每份約 4.4 MB；關閉 `locl` 以避免中文段落內數字替換影響文字複製。使用者不需安裝字型。

## 開發與重現

Node.js 22.12+；`npm ci`、`npm test`、`npm run build`、`npm run dev`。

先執行 `npm run audit:source` 檢查 tracked source、敏感路徑、憑證模式與公開依賴 SHA-256，再執行測試、建置及 `npm run audit:dist`。`.gitattributes` 固定程式的 LF 換行；公開依賴以原始 bytes 保存，確保 Windows/Linux 的資源雜湊一致。

GitHub Actions 在 push main、pull request 與手動執行時，測試 Ubuntu Node 22/24 及 Windows Node 22；包括 `npm ci`、source audit、單元測試、TypeScript/Vite build、dist audit，並保存 Ubuntu Node 22 的靜態 build artifact 七天。私有原檔測試在未提供本機原檔時明確跳過，CI 通過不代表門市實機或原檔 OCR 驗收。

## GitHub Pages 自動發布

`.github/workflows/pages.yml` 在 main 的「Build and test」push 執行成功後，對同一 commit 重跑 source audit、測試、以 `--base=/GTsloth-s-eye/` 建置及 dist audit，再部署到 GitHub Pages；也可在 Actions 頁手動執行（僅限 main）。這條路徑只用 GitHub 內建的 `GITHUB_TOKEN` 與 OIDC，不需任何 Sites credential，也不會碰 Sites 來源庫。

首次啟用（只需一次）：

1. 儲存庫已改為 public（私有儲存庫的 Pages 需要 GitHub Pro／Team 等付費方案）。repo 內沒有私有 PDF 或 credentials，source/dist audit 會擋下禁止路徑與憑證樣式；新增檔案時仍須維持這個前提。
2. Settings → Pages → Build and deployment → Source 選 **GitHub Actions**。
3. Actions → Deploy GitHub Pages → Run workflow（branch: main），之後每次 main CI 通過都會自動部署。

尚未啟用 Pages 時，workflow 只留下警告並略過部署，不會讓 main 變紅。

## 版本與 Sites 發布

1. 從 GitHub main 建立修訂分支，修改 source；發布前以 `npm version patch --no-git-tag-version`（或適當的 minor/major）同步 package.json 與 lockfile。網頁頁尾版本直接由 package.json 產生。
2. 提交、push、確認該完整 GitHub commit 的 CI 全數通過，再請有 Sites 權限的 Codex session 依 Sites skill 發布該 commit。
3. 發布者 fresh clone GitHub 的指定完整 SHA，完成 audit/test/build；以 Sites 原生 credential 與 source helper 開啟乾淨 Sites checkout。只同步經審查的 GitHub tracked source，不複製 Git metadata、node_modules、dist、私有 PDF、fixtures、handoff 或 credentials。不要覆寫 dirty checkout。
4. 以 Sites source helper 執行剩餘檢查/build，commit/push 至原 Sites project `appgprj_6ac91361a0d08191ae079a01fdd25874`，封裝 `.openai/hosting.json` 與 dist。核對封包路徑與版本、排除敏感資料；依序 save_site_version、deploy_site_version，確認終態 succeeded。
5. 在發布紀錄保存 GitHub SHA、Sites source SHA、對應 source tree、archive SHA-256、Sites version/deployment ID 和公開網址。兩個來源庫的歷史不同，commit SHA 可以不同；必須核對對應內容。

GitHub Actions 自動測試、建置並部署 GitHub Pages，但不會自動部署 Sites。現有原生 Sites 工具需要 session 中短效 credential，沒有在這個工作流配置公開網站的永久部署憑證或 GitHub webhook；GitHub push 不會自行更新公開網站。禁止把 Sites token 放進 repo、shell arguments 或 log，僅由原生 helper 的 stdin 使用。Windows package helper 可能需要 Git Bash 在 PATH，以及 `/c/...` 格式的 archive path。

`public/assets/manifest.json` 記錄依賴版本、來源、SHA-256 和授權；`scripts/assets.mjs` 可重下載公開資源。完成後使用 Python 與 `fonttools==4.60.1` 執行 `scripts/static-font.py` 產生 PDF 靜態字型。一般建置不需重新下載資源。完整授權位於 `public/assets/licenses/`。

`qa.html` 與 `scripts/browser-qa.ts` 是本機開發驗證入口，不包含於 Vite 正式輸出。其大量 PDF 功能專供效能測試，不執行人工確認；正式網站的校對關卡始終有效。

私有人工基準存在本機 `tests/fixtures/sample-gold.json`。原範本未隨來源庫發布，缺少該基準時對應測試會明確跳過。`scripts/qa-fixtures.py` 需要原檔，製作 200 頁、續頁、混合文件與超頁數樣本；`scripts/qa.ts` 產生校對基準 PDF；`scripts/verify-pdf.py` 使用 PyMuPDF、Pillow、ZXing C++ 3.1.1 獨立驗證 PDF 與條碼。

實際印表機／掃描器驗收仍需門市設備。先列印三種間距測試頁，逐列確認代號及前導零；若掃到相鄰列，增加列高再測。
