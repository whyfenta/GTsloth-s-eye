# GTsloth-s-eye · 樹懶的工作

首頁是「樹懶的工作」視覺主目錄，共六個功能位置：「樹懶的盤點」、「樹懶的管理」、「樹懶的算數」與三個準備中的保留位置。一般桌面採三欄兩列、手機採兩欄三列；在正常字級與一般螢幕高度下可一頁看完，較小視窗或放大字級時允許捲動以保持可讀性。

盤點工具獨立網址：https://whyfenta.github.io/GTsloth-s-eye/inventory/ ，可直接加入書籤；點盤點頁左上角品牌或手機版「主目錄」即可返回首頁。管理工具網址：https://whyfenta.github.io/GTsloth-s-eye/management/ 。首頁不載入盤點、管理、PDF 或 OCR 模組。

公開網址：https://whyfenta.github.io/GTsloth-s-eye/ （GitHub Pages，main CI 通過後自動部署最新版）。GitHub 公開儲存庫 `whyfenta/GTsloth-s-eye` 是唯一修訂與發布來源。

繁體中文的瀏覽器庫存 OCR 與 A4 條碼盤點表。使用 Vite、TypeScript、PDF.js、Tesseract.js、pdf-lib 與 JsBarcode。

## 樹懶的算數（連處領藥試算）

首頁第三張卡片以「遲領CD」標示今天加 20 天的月／日，每日依台灣時間更新；這是快速參考。內頁沿用盤點、管理的工具名稱導覽與功能主標題，不再顯示快速參考日期，完整試算另依處方條件計算。工具路徑為 `appointment/`，可從主目錄進入，亦可直接開啟。

輸入區上方以「試算／憑單」二選一切換，兩者需要的資料完整度不同：試算可掃碼或手動選日期，右側顯示領藥日期建議；憑單只接受處方 QR（需要姓名、醫院代碼與藥品等完整資料），右側改為領藥憑單。兩種模式各自保留內容，切換不會清除；試算模式的掃碼只解析日期與天數，不讀病人資料。

處方日期整合成「掃碼或選擇日期」單一欄位：聚焦後可直接使用鍵盤式門市掃碼機，或按右側日曆選日期，也可手動輸入西元年／月／日。支援掃碼機以 Enter、Tab 結束或停止輸入後自動帶入，帶入後直接顯示結果。掃碼文字保留空欄並檢查前 14 個固定欄及每 5 欄的藥品結構（健保碼、每次用量、頻率、途徑、總量都不可空白，總量須為正數；每次用量各院寫法不同，如眼科的點眼液與眼藥膏寫 `X1`，網站也不使用，所以不檢查格式）；目前支援這批樣本格式、處方類型 2、28／29／30 天。掃碼機提供的是文字而非原始 bytes，遇亂碼拒絕解析，不能保證恢復錯誤編碼；唯一例外是掃碼機把 Big5 或 UTF-8 的每個位元組各打成一個西文字元（如「測試」變成「´ú¸Õ」），整段都符合時會逐位元組還原再解碼。網頁無法切換輸入法：掃碼欄偵測到中文輸入法正在組字時，捨棄這次內容並提示按 Shift 切換成英數後重掃。民國就醫日期轉西元後帶入處方日期，給藥日份自動帶入；可調劑次數不在 QR 裡，每次掃入會清空成「自動判斷」，已知時再選擇。移除相機、QR 照片及額外的掃描器文字操作區。重掃不代表已領藥。

沿用原試算表的原定領藥區間、最早回診日、失效日及延遲修正公式（失效日當天仍依原表視為有效）；本次領藥日為今天。最後一次後僅顯示回診建議。跨日會更新日期及已試算結果。

**轉盤**：試算沒有按鈕，也不問「本次第幾次領藥」。處方日期、給藥日份與可調劑次數定好後，病患今天拿處方來只有幾種情況：今天領某一次（區間內，或遲領而下一次從今天重算），或今天不領：已開始的最後一次已在別處領過，依正常方式預約下一次。例如第 2 次區間 10/16～10/25、今天 10/30，可能是遲領第 2 次、第 2 次已在別處領過而預約第 3 次，或少見的連第 1 次都還沒領。這些結果全部算好，依時間順序排在結果區的轉盤上：今日領第 1 次、第 2 次……到已開始的最後一次，最後一格是「今日不領」（最後一次也領完時改為提示回診並給最早回診日）。還沒開始的次數不會出現，因為那就是今日不領要預約的那次。填好處方日期與給藥日份就出現，改任何欄位立即重算（手動打的日期在按 Enter 或離開欄位時才算）。轉盤是固定大小的視窗，一次顯示一格，上下露出前後格的邊；在轉盤上捲動滑鼠滾輪一次轉一格，到頭尾時才捲動頁面，也可以按上下方向鍵、PageUp／PageDown、Home／End、右側 ▲▼、點上方刻度直接跳格，手機上下滑動。一開始停在依今天日期推算的那格，標示「推算」：今天在某次區間內，停在今日領那次；區間已過、下一次還沒開始，停在今日不領（通常是已在別處領過、來預約）；最後一次的區間也過了（處方還沒失效），停在今日領最後一次（遲領）。可調劑次數留「自動判斷」時，每格並列 2 次與 3 次的結果，內容相同就只顯示一次；兩者推算的格子不同時（例如已過第 2 次區間：2 次推算為第 2 次遲領，3 次推算為今日不領），停在較後面的那格。某個次數處方日期未到或已失效時，在轉盤上方列一次原因，不放進轉盤。轉盤下方的時程表以底色標出轉盤目前這格的那次（今日不領標要預約的那次）。

**前次逾期領藥日**（選填，只在轉盤的「今日不領」格）：已在別處領過、但當時逾期才領時，給藥期間從實際領藥日重新起算。在今日不領格的「第 n 次實際領藥日」填處方箋背面的調劑日期，要預約的下一次區間與最早回診日改從這天往後推（與延遲修正同一公式，仍受原處方失效日限制，起日不早於失效日的次數視為已無，改為提示回診）；格內標示「依前次 M/D 逾期領藥順延」，時程表的順延列後面以淡色小字附原定日期，只改今日不領格與時程表，不影響今日領各次的結果。在區間內領的不會順延，格內提示「前次領藥日未造成順延，時程不變」；早於該次區間或晚於今天時提示核對。日期欄可直接打字，打到完整日期才重算，游標留在欄位裡；在欄位內按方向鍵只改日期、不轉動轉盤。改任何表單欄位、掃入新的 QR 或清除重填會清空此欄，跨日則保留。限制：只認前一次的日期；若第 1 次逾期、第 2 次在順延後的區間內領，第 3 次的區間仍以第 2 次的原定給藥期間計算，可能偏早幾天（與未填此欄時相同）。憑單模式尚未支援此欄。

解析與試算完全在瀏覽器執行，不上傳、持久儲存或記錄病人資料；掃碼原文解析後清除。試算結果不顯示病人識別資料，領藥憑單則見下方說明。未連接庫存，不扣庫存；憑單以網站內附的商品代號查詢檔把藥品查成六碼，不另做名稱比對（見下方「商品對照檔」）。單元測試及瀏覽器驗證採合成 QR 文字；原始 8 張照片未提供於本專案，不能視為已完成原樣本或門市掃描設備驗收。

### 領藥憑單

切換到「憑單」後，每掃一張處方 QR 就加入右側的「領藥憑單」，版面沿用會員中台「列印憑單」：A4 上半張「領藥憑單」給病人，下半張「門市存查」。同時交付多科或家人的處方時連續掃入即可合併；同一張重掃不會重複加入。寬螢幕上，左側「輸入處方資料」卡片會隨捲動停在畫面頂端，填到憑單下方時仍可隨時點掃碼欄掃下一張。

- **次數**：QR 不含可調劑次數，預設 2 次。掃入後游標移到該張的「可調劑次數」，以方向鍵選 2 或 3、Enter 確認後移到「本次第幾次」；本次第幾次預設依日期推算（標示「推算」，可調劑 2 次時不能選第 3 次），同樣以方向鍵選擇，Enter 確認後游標回到掃碼欄等下一張。掃入後 0.3 秒內的 Enter 不算，以免掃碼機多送的 Enter 直接確認預設值。滑鼠點選也可以。
- **藥品較多的處方（兩個 QR）**：藥品多的處方會印第 2 個 QR，只有藥品欄位（每 5 欄一個藥，沒有前 14 個固定欄），第 1 個 QR 也沒有任何欄位表示後面還有。掃到這種只有藥品的 QR 時，藥品接在最後掃入的那張處方的尚差藥品後面（標示「含藥品 QR 加入的 n 個藥」），處方警示一併比對；重掃同一個不重複加入。它沒有姓名與日期，無法核對是不是同一張，請先掃第 1 個 QR 再接著掃第 2 個；接錯時按該張的「移除」重掃。掃完第 1 個 QR 後游標在可調劑次數，此時直接掃第 2 個也會自動回到掃碼欄。還沒掃任何處方、或憑單已列印時掃到，提示先掃第 1 個 QR。試算模式只需要第 1 個 QR，掃到第 2 個時提示並保留原本的欄位。收集頁同樣把第 2 個 QR 接在上一行，並統計哪些院所有這種處方（見下方「處方樣本收集」）。
- **預計領藥日**：日期用樹懶算出的區間，延遲時用修正區間。多張處方依「趟次」取共同區間：下一趟是每張處方下一次區間的交集，再下一趟是還有剩餘次數的處方的交集；日期旁的 x 為該趟涵蓋的處方張數。有兩趟時分別填「第二次」與「第三次」列；只有一趟時，每張都是第 3 次才填第三次列（與範本一致），否則填第二次列。找不到共同可領藥日時不能列印，畫面列出每張的區間，請移除部分處方分開開立。延遲領藥後的再下一次區間要等這次領完才能算，先留白。計算出的區間是預設值；病患另有約定時，可在「預計領藥日」逐列調整起訖：日曆選擇，或方向鍵前後一天（↑→ 晚一天、↓← 早一天），Enter 移到下一格，最後一格之後到聯絡電話。調整後的日期不能早於今天、晚於領藥最終有效時間，起日也不能晚於訖日；超出計算區間時預覽會提醒確認是否符合領藥規定，並列出原計算值，可按「還原計算值」。再掃入處方或修改次數使計算區間改變時，調整會改回新的計算值並提示。已是最後一次（含延遲後只剩回診的情況，例如可調劑 2 次的第 2 次延遲）不填預計領藥日，也不填回診日期；這種憑單通常是為了缺藥。
- **領藥最終有效時間**：取各張處方失效日的前一天中最早的一天。以範本處方 2026/09/24、28 天 × 3 次核對，會員中台印 12/16，樹懶的失效日為 12/17。
- **病人資料**：姓名從 QR 第 4 欄帶入，多人時以「、」並列，太長自動縮小字。身分證（第 5 欄）與生日（第 6 欄，民國轉西元）只印在門市存查聯底部，格式為「身分證.西元生日」；病人聯完全不含身分證文字。這兩欄的位置已以真實處方 QR 核對（第 3 欄不是身分證）。
- **醫院名稱**：用 QR 第 1 欄醫事機構代碼查「健保特約醫療院所名冊」，可手動修改；第一次掃碼時才載入名冊。查不到代碼時，畫面會提示可能是新特約院所，並附上更新名冊的下載位置。
- **尚差藥品**：每張處方的 QR 藥品預設不缺，有缺才勾選，再填門市實際缺的數量（不預帶 QR 總量，因為不一定整份都缺），可補品名與備註；另可加「其他」列（如自費品項）。憑單只有 4 列，「尚差＿種藥品」自動填品項數。
- **商品對照檔**：QR 的藥品是健保碼。網站內附由商品代號對照檔（private repo `GTsloth-map` 的 `sku-nhi-map.csv`，格式見 [`docs/reference/sku-nhi-map.md`](docs/reference/sku-nhi-map.md)）產生的查詢檔 `public/assets/nhi/products.json`，只含健保碼、六碼與對接品名，不含判定、判定日期與來源門市；第一次掃碼時自動載入（約 0.3 MB，gzip 約 0.1 MB）。對照得到的健保碼在勾選清單顯示「六碼 品名」，勾選後憑單的品項編號印六碼、品名預先帶入（可修改）。品名去掉開頭的包裝規格（如 `1000粒/盒(10粒/排)`）以放進憑單的品名欄。同一健保碼對到多個六碼（同藥不同包裝，例如瓶裝與盒裝）時，勾選清單列出全部六碼，勾選後須從含包裝的完整品名選出缺的是哪一個，未選不能列印。查詢檔沒有的健保碼照舊顯示並列印健保碼，品名自填。對照檔更新後，執行 `npm run slip-assets -- --map ../GTsloth-map/sku-nhi-map.csv` 重產查詢檔並更新 manifest，再依一般流程發布。
- **其他欄位**：聯絡電話、簡訊發送／電話通知、備註、承辦人員現場填寫；單號留白（以白框蓋住底圖的範例字）。承辦人員在清空憑單後保留。
- **列印**：按「列印憑單」開啟瀏覽器列印，請用 Chrome 或 Edge、A4、100% 原尺寸、邊界「預設」或「無」。只在列印時組出憑單，列印完即清除；列印後下一次掃碼自動開始新的憑單，避免不同病人被合併。輸入處方資料卡片右下角的「清空憑單」（按下後需再確認）或關閉頁面也會清除。

**更新醫院名冊**（出現「查無醫事機構代碼」或定期更新時）：到政府資料開放平臺「健保特約醫療院所名冊」 https://data.gov.tw/dataset/168341 下載 CSV（資源 `A21030000I-D2100G-001`），**不要先用 Excel 開啟**（Excel 會去掉代碼開頭的 0，並把部分代碼變成科學記號），再執行 `npm run slip-assets -- 路徑/A21030000I-D2100G-001.csv`。程式只保留醫事機構種類 A（醫院、診所）的代碼與名稱，寫入 `public/assets/nhi/institutions.json` 並更新 manifest；無法還原的代碼會列出並略過。目前名冊資料日期 2026/10/24，共 25,344 筆；來源檔有 7 筆代碼已是科學記號，這 7 家診所的處方會出現查無代碼的提示。資料依政府資料開放授權條款第 1 版使用，顯名聲明見 `public/assets/licenses/OGDL-Taiwan-1.0.txt`。

### 處方警示（試用，預設關閉）

憑單模式每掃入一張處方，比對 QR 的診斷碼（ICD-10-CM）和每個藥的 ATC，在該張處方卡片下方列出和本次診斷對不上的藥，讓藥師在忙碌時也能發現可能開錯的藥，例如藥名相似而拿錯、病人或處方弄錯。規則用知識庫分層判定，不做統計關聯，所以不需要蒐集病人資料。

- **開關**：規則表是草稿，**預設關閉**，藥師審完才打開。試用時在網址加上 `?rxcheck=1`，例如 https://whyfenta.github.io/GTsloth-s-eye/appointment/?rxcheck=1 ，只對這次開啟的頁面有效，不儲存；`?rxcheck=0` 關閉。審完後把 `src/rx-check-config.ts` 的 `RX_CHECK_DEFAULT` 改成 `true` 再發布，所有人預設開啟（仍可用 `?rxcheck=0` 關閉）。試算模式不顯示警示。
- **畫面**：每張卡片下先列出科別、年齡層與本次診斷（附中文名稱），紅色、黃色警示直接顯示，灰色提示與已由某一層解釋的藥收在「灰色提示 n 則・已解釋 m 個藥」，點開才看到。每則一行：藥名（商品對照查得到時用品名，否則用健保成分）、ATC 與理由，理由裡的診斷碼附中文名稱。警示不印在憑單上。
- **判定**：每個藥依序看適應症、同處方的其他藥、科別常用、低風險，前一層解釋得了就停；都解釋不了時高警訊藥給黃色、其他給灰色。注意事項（診斷、年齡、同處方）與同成分重複另外判定。沒有診斷碼的處方只給一則灰色提示；不在健保用藥品項的代碼（例如特材）當成低風險。規則表、寫法與待藥師確認的事項見 [docs/reference/rx-rules.md](docs/reference/rx-rules.md)。
- **讀取的 QR 欄位**：第 7 欄就醫科別（2 碼；補成 4 碼的如 `AB00`、`0100` 取前 2 碼；院內 3 碼如 `146`、`0NB` 當作未知科別）、第 12 欄診斷碼（`#` 分隔，有無小數點與結尾 `#` 都可以）、第 6 欄生日（只用來算年齡層，與收集頁相同：每 10 歲一級，60～69 歲在 65 歲切開），以及每個藥的健保碼、頻率、途徑；大小寫與多餘空白不影響。這些只留在頁面記憶體，和姓名一樣不儲存、不送出。
- **資料檔**：`public/assets/rx/` 的規則表（`rules.json`，約 21 KB）、健保碼對 ATC 與成分（`drugs.json`，約 1.8 MB，gzip 約 0.36 MB）、ICD-10-CM 中文名稱（`icd10cm.json`，約 6.3 MB，gzip 約 0.64 MB），開關打開後第一次掃碼時整份載入。診斷名稱不依章節分檔按需載入，因為那樣請求的網址會透露這位病人的診斷章節。改了 `docs/reference/rx-rules/` 的規則表，或更新 `docs/reference/` 的健保用藥品項、ICD 對照檔後，執行 `npm run rx-assets` 重產並更新 manifest（`npm test` 會檢查有沒有重產）。健保署資料依其政府網站資料開放宣告使用，出處見 `public/assets/licenses/NHI-open-data.txt`。
- **測試**：單元測試只用合成 QR 與合成規則表。和規則草稿的 Python 原型逐藥比對的測試需要本機的去識別化樣本，以環境變數 `RX_SAMPLES`（樣本檔，Windows 以 `;` 分隔）與 `RX_PROTOTYPE`（`check_rules.py`）指定，未指定時跳過；目前 171 張、558 個藥全部一致。
- **後續工作**：藥名相似（LASA）提示、左右眼比對、過敏比對、給付期間檢查、規則表的出處與審核欄位、接入食藥署「全部藥品許可證資料集」的適應症原文。

## 處方樣本收集（處方 QR 去識別化）

網址：https://whyfenta.github.io/GTsloth-s-eye/collect/ （不在首頁導覽，直接分享網址）。用途是為規則式處方警示（比對 ICD-10 診斷碼與藥品，找出「藥和診斷對不上」的處方）收集各院所、各科的真實處方樣本：門市值班同事用鍵盤式掃碼機連續刷處方 QR，每一張在瀏覽器裡去識別化，最後按「複製全部」或「下載 .txt」交給藥師，檢查各院所的格式差異與規則涵蓋度。

掃碼欄沿用樹懶的算數的處理方式：Enter、Tab 結束或停止輸入 0.4 秒後解析；QR 文字不會留在欄位上；UTF-8／Big5、掃碼機逐位元組打字的還原，以及中文輸入法組字時捨棄並提示按 Shift 切換英數，都與算數相同。收集範圍比試算寬：不限處方類型與給藥日份，只檢查結構（前 14 欄固定、之後每 5 欄一個藥品，至少一個藥品）與每個藥品的健保碼不可空白；每次用量、頻率、途徑、總量空白時照樣保留成空欄，寫法也不檢查。另有一項隱私檢查：照原樣保留的第 1、2、8、10、12 欄只能是英數與半形符號，出現中文或全形字表示可能是不同的 QR 格式（姓名可能落在保留的欄位），整張改記失敗。

每張處方輸出一行，維持原本以 `;` 分隔的欄位與位置（結尾同樣多一個 `;`），刪掉的欄位留空、不移位。保留欄位若含換行（CR、LF 或 Unicode 行／段分隔符），整張改記失敗，避免一張被拆成多行。欄號從 1 開始：

| 欄 | 內容 | 輸出 |
| --- | --- | --- |
| 1 | 醫事機構代碼 | 保留 |
| 2 | 處方類型 | 保留 |
| 3、7、11 | 用途不明 | 1～4 碼英數字才保留，否則留空 |
| 4 | 姓名 | 清空 |
| 5 | 身分證 | 清空 |
| 6 | 民國生日 | 以第 8 欄就醫日期算足歲，改成每 10 歲一級的年齡層，如 `AGE70-79`；60～69 歲在 65 歲切開為 `AGE60-64`、`AGE65-69`（老人用藥規則以 65 歲為界）；未滿 10 歲 `AGE0-9`，90 歲以上 `AGE90+`。生日讀不出來（不是民國七碼日期）時不記原值，只記格式形狀：數字換成 `9`、英文字母換成 `A`、其他非 ASCII 字元（含中文、全形字、換行）換成 `X`、半形符號照原樣，如 `AGE?9999/99/99`；形狀超過 12 個字元只記長度，如 `AGE?len15`。生日空白、就醫日期無法解析或生日晚於就醫日時留空 |
| 8 | 民國就醫日期 | 保留 |
| 9 | 用途不明 | 清空 |
| 10 | 給藥日份 | 保留 |
| 12 | ICD-10 診斷碼（`#` 分隔） | 保留 |
| 13 | 用途不明（樣本中與第 1 欄相同） | 與第 1 欄完全相同才保留，否則留空 |
| 14 | 以逗號分隔的多段 | 只保留 `過敏史:`（或全形冒號）開頭的那一段，其餘清空；過敏史文字裡的半形逗號會被當成分段，逗號後的內容一併清空 |
| 15 起 | 藥品，每 5 欄：健保碼、每次用量、頻率、途徑、總量 | 保留；健保碼空白時整張記失敗，其餘四欄空白時保留成空欄 |

**兩個 QR 的處方**：藥品多的處方另有只有藥品欄位的第 2 個 QR（判斷方式見上方「領藥憑單」）。刷到這種 QR 時，藥品欄位照原樣接在上一行的結尾，所以同一張處方仍是一行、仍是 14＋5n 的欄位格式，藥師的比對程式不用改；上一行不是成功收下的處方（還沒刷、或解析失敗）時記一行失敗。重刷同一個第 2 個 QR 不重複接上。它沒有病人與日期，無法核對是不是同一張，請先刷第 1 個、緊接著刷第 2 個。左側的「有第 2 個 QR 的院所」依醫事機構代碼列出有幾張處方帶第 2 個 QR、該院所共收幾張，按「複製統計」複製成文字。按「下載 .txt」時，有第 2 個 QR 的處方就另外下載一個 `處方QR去識別化_日期_n張_統計.txt`，內容同複製統計（第一次會詢問是否允許下載多個檔案，請按允許）；樣本 .txt 本身只有處方行與失敗行，因為藥師的比對程式把其他每一行都當成處方，從樣本 .txt 也看不出哪一行接過第 2 個 QR。瀏覽器保存的結果會一併記下每一行由幾個 QR 組成，重開分頁後統計仍在；這次更新前保存的結果都當成一個 QR。頁面不連線，所以只列代碼、不查院所名稱。

解析失敗時不記原文，只記一行 `失敗：原因，欄位數 n`，方便了解其他院所的格式；沒有以分號分隔欄位的掃碼（如藥盒條碼）不是處方 QR，只提示、不記錄。畫面上的張數只算成功的處方，失敗另計次數。

**重複**：同一張處方在這次使用中重刷，提示已在第幾行、不重複加入。比對的是掃碼原文的 SHA-256 摘要（原文本身解析後即丟棄，摘要只在頁面記憶體），所以兩位病人去識別化後內容剛好相同，仍會各記一行。重新整理或誤關分頁後重開，之前的摘要已不在：之前收的處方重刷時改用去識別化結果比對，相同就視為重複；之前的失敗行則無法判斷。

**清除**：「清除」會先跳確認，清除後無法復原，請先複製或下載。確認清除也會取消尚未完成的掃碼與等待中的匯出。複製與下載會先等先前刷入的掃碼完成，才產生完整結果。下載檔名為 `處方QR去識別化_西元日期_張數張.txt`，UTF-8、一行一張。

**隱私**：掃碼原文只在解析當下留在頁面記憶體，解析完即丟棄，不寫進任何儲存、不輸出到 console、不送出。去識別化後的結果（含失敗行）存在這台電腦瀏覽器的 `localStorage`（鍵 `gtsloth-qr-samples`），誤關分頁重開仍在，按「清除」才刪除；頁面上以一句話說明保存與不保存的內容。同一台電腦同時開兩個分頁收集會互相覆蓋，頁面偵測到時會提示只留一個分頁。頁面以 Content-Security-Policy 禁止任何連線（`connect-src 'none'`），除了載入頁面本身的程式與樣式不發出網路請求，也不載入醫院名冊或商品查詢檔。輸出仍含醫事機構、就醫日期、年齡層、診斷與藥品，屬於去識別化後的醫療資料，交給藥師時請用內部管道。單元測試只用合成 QR。

## 使用

1. 選擇或拖放一份或多份 PDF、JPG、PNG，可分次加入、逐份移除；合計最多 200 頁、200 MiB，同一檔案不會重複加入。加入時只檢查格式、頁數與解析度，不會開始辨識；全部加入後按「開始辨識」。辨識完成後會自動捲到下一個待操作卡片：有疑義時進入校對，沒有疑義時進入產生盤點表。辨識完成後再加入或移除檔案，會先詢問並清除目前結果。庫存簡表可在樺穎的 IM1C1 依自訂條件設定簡表範圍後，將印表機設定為「列印至 PDF」產生。
2. 等候逐頁辨識；暫停會完成目前頁才停下。取消會終止 OCR Worker，之後可按「重新開始辨識」。多份檔案時先讀每份的第一頁，比對表頭上方的門市名稱：全部相同才繼續讀其餘頁面；兩份由 PDF 文字直接讀到的名稱不同即停止，須移除不同門市的檔案再重新開始；名稱讀不到，或含掃描辨識結果而不一致時，列出各份的名稱請人工確認是否同一門市，確認後才繼續。每份檔案各自判斷方向與欄位位置，不沿用其他檔案，因此每份的第一頁都要有表頭。
3. 校對代號、名稱、儲位及帳量。預設「只看有疑義」會彙整所有頁面的待確認列；點「對照」可看原始列與原名稱，名稱前綴可在對話框修改。沒有疑義時會明確顯示可直接產生盤點表。
4. 有疑義的列已標色並在名稱下列出原因（只是說明已依格式移除前綴的提示不標色）；需要勘誤時直接修正欄位，代號或帳量辨識不一致時點選原圖旁的候選值。疑義項目調整後，勾選各列旁的「已確認」；全部疑義確認後即可輸出，無疑義品項自動放行，不需整頁或最終總勾選；確認後再修改任一欄，該列會回到待確認。可關閉「只看有疑義」逐頁瀏覽，← → 手動換頁，欄位中按 Enter 移到下一列。儲位空白是一般值，不列為疑義。辨識到帳量為 `0` 的安全列不會進入校對或輸出；負數保留。多份檔案的資料合併：不同檔案中同代號、同儲位且帳量相同的列視為重複，只保留一筆（保留較清楚的辨識；已確認的列不會被取代），頁面選單與統計顯示刪除筆數；帳量不同時兩筆都保留，標為須逐筆確認的疑義，改成一致後輸出只印一筆。同一檔案內的列一律不合併。所有來源頁必須通過格式檢查，全部疑義須確認，才能輸出。
5. 選擇六編碼或儲位排序、22.6 / 25.8 / 29 mm 最低列高，下載 PDF。無論哪種排序，帳量為負數的品項都先排在最前，之後才是正數品項，方便優先處理。印表機使用 A4 直式、100% 原尺寸。

**盤點資料時效提醒**：以台灣日曆日期計算，來源庫存簡表的列印日距今天已達 **3 天（含）** 時，輸出區與產生的 PDF 第一頁都會以加大粗體顯示「【提示】」，提醒庫存可能與現況不符，建議重新列印最新庫存簡表。例如今天為 10/21，10/18（含）以前列印即提醒，10/19 不提醒。多頁、多檔以所有來源頁面中最早的列印日期判斷，含帳量為 0 或已去重的頁面；文字 PDF 直接擷取日期，掃描檔另辨識頁尾列印日期。未讀到日期的頁面會在畫面與 PDF 提醒人工核對時效。警語不阻擋校對或輸出；跨日重新預覽或下載時會更新警語。管理工具維持 7 天（含）的警語門檻，兩種工具均以台灣日期判斷。

範本是掃描文件，中文藥名、包裝字形、儲位「三／二／四」與千分位容易誤辨；OCR 結果不是校對後資料。保留劑量、劑型及末尾 `(管3)` / `(管4)`，不以藥品字典猜測替換。

## 樹懶的管理（安全量、呆藥、空位清單）

1. 「庫存簡表」與「醫品調劑數量統計表」各有一個匯入區：庫存簡表可加入多份 PDF、分次補頁；醫品調劑數量統計表一次只匯入一份，要更換時先移除原檔；合計最多 400 頁（含零庫存列印的庫存簡表可達約 150 頁，加上調劑表仍可一次匯入；盤點工具維持 200 頁）、200 MiB，以 SHA-256 判斷同一檔案不重複加入。**只接受系統列印、沒有圖片的文字 PDF**；掃描檔、圖片檔或含隱藏 OCR 文字層的頁面一律拒收，本功能不做 OCR。解析完成後會自動捲到待處理卡片：來源待核對時到來源核對、有疑義時到校對資料、其餘到產生清單。全部疑義逐筆確認、整頁確認或排除完畢後，會再次自動捲到下一個人工檢核卡片。按「開始解析」後先讀每份檔案第一頁核對報表種類與門市，再讀其餘頁面。放錯區的報表會說明應放的位置並停止。
2. 每頁都須印有表頭、門市與原報表頁次（庫存簡表 `頁次 n of total`，調劑表 `頁次：n/total`），調劑表另須有統計期間與給付方式。各頁的門市、期間、給付方式、總頁數與列印日期須一致，不同期間或篩選條件不會混算。庫存簡表的補頁檔可從原報表第 2 頁開始；缺頁、同頁碼內容不同會阻擋計算；完全相同的重複頁只計一次。同一報表中同碼的多筆調劑明細是合法資料，一律加總。
3. 門市以「門市編號＋店名」識別：調劑表「營業點：0026 26永和福和店」與庫存簡表「26北-永和福和店」視為同店；庫別不單獨作為門市依據。門市編號不同即拒絕，人工確認也不能覆蓋；只有無法自動判斷時才請人確認。庫存列印日早於調劑截止日只提示，不拒收。任一份報表的列印日期距今已達 7 天（一週）以上時，來源核對與產生清單處都會顯示警語，三份 PDF 第一頁表頭也會以加大粗體印上「【警語】…輸出結果可能失真」，提醒重新列印最新報表。
4. 調劑表的文字儲存順序與版面不同，依座標分欄：代號與名稱依起點、右對齊的次數、數量與健保價依終點。健保價（每單位）只用於安全量清單的待採金額標示：缺少或同列出現多個值時列入校對，非數字或負數須修正或清空，空白不阻擋計算（該品項不標示）。庫存簡表沿用盤點的文字層解析，取庫存量不取寄庫量。代號以字串保存。非六碼列（如 `R001`）保存為排除紀錄、不計入 N，修正代號後可「恢復此列」；缺代號但有數值的列、負數、缺單位、同碼不同單位、同碼同儲位重複等須修正或附理由排除，不能一般勾選放行。可對照原報表該列的影像。名稱沿用盤點的前綴清理，**只有本功能保留「缺貨」與「冷藏」**（`缺貨 PENTOP…`、`冷藏 Delta Pen…`；兩者皆有時一律印成 `缺貨冷藏 …`），其後的 `C-`、包裝等照常清除。
5. 產生安全量清單前可選擇三張策略卡，預設為**平衡派**：

   | 策略 | 係數（高頻 → 低頻） | 主要優勢 | 主要需求 |
   | --- | --- | --- | --- |
   | 倉鼠派 | 3.5～1.2 | 供貨不穩定時仍有充足貨源 | 較大的調劑與儲存空間 |
   | 平衡派 | 2.5～0.8 | 較寬的係數梯度保留高頻用藥，從較低頻用藥節省空間 | 兼顧備貨餘裕與儲存空間 |
   | 羚羊派 | 1.2～0.6 | 精控備貨量以配合固定倉儲空間 | 更密切、頻繁地關注貨源 |

   計算使用精確分數，最後才進位：統計月數依日曆月，區間為 `[起日, 截日+1日)`，以起日日號為每月錨點（月末截到該月最後一天），餘天除以該錨點月段的天數；2026/06/16～2026/10/15 為 4 個月。`A = 合計次數 ÷ 月數`、`B = 四捨五入(合計數量 ÷ 合計次數)`、月用量 `A × B`；係數依品項在本門市清單內的 A 排名決定（第 i 名，0 起算，`p = 1 − i / (K − 1)`，同 A 同名次）：前 1/3（`p ≥ 2/3`）採策略最高係數，其餘為 `最低係數 + (最高係數 − 最低係數) × p ÷ (2/3)`，末位採最低係數，僅一筆時採最高係數；六碼經商品代號對照（`public/assets/nhi/products.json`）查到的健保碼為 A 開頭者，係數 × 0.85，非 A 開頭或查無健保碼者維持原量（對照檔載入失敗時不套用並提示）；品名保有「缺貨」前綴的品項（以清單印出的名稱判斷）係數再 +1，此 +1 在 × 0.85 之後；保有「冷藏」前綴的品項，因冷藏空間固定、不容超量，係數（含缺貨加成後）再 × 0.8，冷藏在最外層、最後才乘；兩者只影響建議安全量，不改變入選與排名；建議安全量 `ceil(A × B × 係數)`。倉鼠派保持原曲線（其餘名次為 `1.2 + 3.45 × p`）；係數代表要備幾個月的用量。N 為不同的有效六碼數；`K = min(floor(N × 10%), A > 8 的品項數)`，依 A 降冪、同值依六碼，不擴增 K，N < 10 時可為 0 筆。切換策略會即時更新安全量預覽，品項篩選、合作診所判定及呆藥／空位規則維持一致；同一頁重新解析或更換檔案會保留策略選擇。
6. 安全量清單 PDF 標題為「安全量調整及採購建議清單」，欄位依序為六編碼、品名、現有庫存量、調劑頻率(/月)（A）、均月銷（A × B）、建議安全量、待採量；`待採量 = 建議安全量 − 現有庫存量`，庫存已足夠時記 0，簡表無此碼時印「—」。現有庫存量**大於 4 倍均月銷**（4 個月用量，恰為 4 倍不標示）時以紅色粗體印出（預覽同樣標示）：開立處方的醫院若指定換藥造成用量銳減，這些藥的逾期耗損風險較高。**待採量 × 健保價大於 1,000 元**（恰為 1,000 元不標示）時，待採量以紅色粗體印出（預覽同樣標示），提示優先採購這些品項可更快達到免運門檻；同一六碼在調劑表印有兩種健保價（期間內調價）時以**低價者**計算，紅字即表示以低價計仍超過 1,000 元；名稱尾綴含 `(管3)`、`(管4)` 的管制藥只能申請、沒有自行採購管道，一律不標示（計算與其他規則不變）；待採量印「—」或健保價空白的品項不標示。清單每碼一列，庫存量為同碼各儲位合計、名稱取庫存簡表第一筆。調劑表有碼而庫存簡表沒有可以是合理差異，不補 0、不從 N 移除，也不需額外確認或阻擋輸出。落在安全量清單內的品項，現有庫存量欄印「簡表無此碼」、待採量印「—」，名稱改用調劑表名稱（可能被截短）；畫面不另列缺碼核對區塊。
   **合作診所供貨的門市**：先依一般規則排出安全量清單；其中**本店無庫存**的六碼（庫存簡表沒有任何列，或各儲位庫存合計為 0）**超過 10 個**時，判定此門市有合作診所供應部分貨源（10 個以下仍視為本店品項：沒有列的照上述方式標示「簡表無此碼」，庫存 0 的照印 0）。庫存合計為 0 與「簡表無此碼」意義相同，因為含零庫存列印的簡表會列出整個商品檔（0015 的清單 171 筆中有 96 筆庫存為 0）；判定後，這些無庫存的六碼，以及庫存不足 0.1 個月用量（約 3 天，含負庫存；15 南崁店 45 筆、占清單用量 40%，26 永和為 0；使用者可在來源核對區勾選放寬為 0.2 個月，約 6 天，讓更多品項遞補，但本店庫存偏低、確需採購的品項也可能一併被略過，畫面與 PDF 會註明此風險；預設仍為 0.1，重新匯入檔案會回到預設）的六碼，視為主要由合作診所供應，不由本店監控安全量：安全量清單略過它們，由 A 排序的後一位向前遞補，N 與 `floor(N × 10%)` 不變，K 仍不超過「A > 8 且本店有庫存」的品項數；沒有列的六碼不需勾選確認。來源核對區與清單 PDF 表頭／頁尾會註明判定依據、略過與遞補筆數。
7. 呆藥（庫存量 ≠ 0）與空位（庫存量 = 0）取不在調劑表有效六碼集合中的庫存列，保留各儲位、依盤點的儲位排序（空白在後）；負庫存照列並標「負庫存異常」。呆藥清單最右欄為**建議處置**：狀態前綴（`A-`／`B-`／`C-` 標記前）含「冷藏」「缺貨」「追追」，或名稱含 `(管4)`、`(管3)` 等管制藥標示的品項，依此順序（冷藏 → 缺貨 → 追追 → 管4 → 管3 → 管2 → 管1，以最先符合者為準）排到清單最前並建議「轉調協銷」，其餘建議「月初退倉」；各組內仍依儲位排序。**自費品項**（庫存簡表名稱在 `A-`／`B-`／`C-` 標記前的狀態文字含「自費」，如 `自費C-`、`!自費B-`、`換包自費C-`、`停供自費避光C-`）不符健保規則、不計入健保調劑，未出現在調劑表不代表滯銷，因此不列入呆藥或空位：庫存不為 0 者以灰字接續附於呆藥清單末、建議處置一律為「待判定」，前有一列「以下品項偵測應為自費品，耗量不在健保調劑量統計內，但機械判別難免有誤，請過目。」，不計入呆藥筆數（表頭註明另附筆數）；庫存為 0 者不列出。只認名稱前綴：類別 `0970` 混有非自費品項，不作為依據；未標「自費」的自費品項仍會列為呆藥，應在商品檔名稱補上前綴。來源檢查與資料校對完成後，呆藥與空位清單均要求統計期間**嚴格大於 2.5 個月**（恰為 2.5 個月仍不開放），不再要求人工確認儲位範圍或限定給付方式。空位清單另須有庫存為 0、且未出現在調劑統計內的有效品項才開放；兩份清單均不限定給付方式；沒有符合品項時卡片灰階停用。不再提供儲位範圍與包含零庫存的確認方塊，輸出範圍以匯入的庫存簡表為準。
8. 三份 A4 直式 PDF 以卡片選取，預設不勾選；資料不足的卡片會灰階、停用並說明原因。勾選「安全量調整及採購建議清單」後，才在該卡片內選擇安全量策略；取消勾選會收起策略，再次勾選會保留所選策略。勾選的清單可展開資料預覽，產生後可各自預覽、下載 PDF。名稱換行、整列不跨頁，每頁保留清單標題、欄名與頁碼；門市、統計期間、來源檔名、校對版本、程式版本及逾期警語僅第一頁印出；安全量清單標題附策略名稱與係數範圍、下載檔名附策略名稱；安全量清單頁尾只印紅字的說明「紅色：品名保有「缺貨」前綴（供應商缺貨）；紅色粗體：現有庫存量 > 4 倍均月銷，醫院換藥致用量銳減時易逾期耗損；待採量 × 健保價 > 1,000 元，優先採購可更快達免運門檻（(管3)(管4)管制藥只能申請，不標示）。」（網頁資料預覽下方同樣列出；缺貨品項品名開頭的「缺貨」二字以紅字印出，PDF 內嵌字型只有一種字重，故只變色不加粗）（逾期警語改於第一頁表頭以加大粗體紅字印出），公式不在 PDF 重複，省下的頁尾行數讓表格多容納列數；無資料時印出說明頁。任何來源、校對、確認、策略或勾選變更都會使已產生的 PDF 失效。

## 資料與隱私

- 沒有檔案上傳 API、庫存資料庫、分析追蹤、外部 OCR 服務、LocalStorage、IndexedDB 或 Service Worker。
- 例外：處方樣本收集把去識別化後的結果存在瀏覽器的 LocalStorage（見上方「處方樣本收集」）；掃碼原文不儲存。
- 另一個例外：樹懶的管理產生 PDF 時，會把校對修改紀錄（見上方「校對回饋」）送到 `src/feedback-config.ts` 設定的 Google Apps Script 網址；報表檔案、店名、統計期間與任何數量都不送出。
- 樹懶的算數的領藥憑單會在畫面與列印中顯示病人姓名，門市存查聯另印身分證與生日；這些資料只在當次頁面記憶體，不儲存、不送出。處方警示（預設關閉）讀取的診斷碼、科別、年齡層與藥品也一樣；它的規則表、藥品與診斷名稱資料檔整份載入，請求不因處方內容而不同。醫院名冊、商品代號查詢檔（健保碼、六碼、品名）與憑單底圖是網站本身的公開資源；商品代號對照檔本身與其判定、來源門市仍留在 private repo。
- 使用者檔案、原圖裁切與結果只存在當次頁面記憶體。圖片檔只在辨識或檢視原圖時解碼，加入多張照片不會同時佔用解碼後的記憶體。清除／關閉／重新整理會失去資料；下載 PDF 由使用者裝置保存。
- OCR 模型、Worker、WASM、PDF.js 字型資源及中文字型均從網站本身載入。HTTP 快取可能保存公開依賴資源，不保存庫存文件。
- 原始庫存 PDF、人工基準 JSON、測試影像、輸出及詳細辨識紀錄留在本機，Git 忽略這些資料，部署封包只有靜態程式與公開依賴資源。

## 校對回饋試算表（設定一次）

1. 在 Google 雲端硬碟建立一份試算表（例如「樹懶的管理 校對回饋」），選單「擴充功能 → Apps Script」，把 `docs/feedback-apps-script.gs` 的內容整份貼上並儲存。
2. 「部署 → 新增部署作業」，類型選「網頁應用程式」；執行身分選「我」，存取權選「所有人」。授權後複製結尾為 `/exec` 的網址。
3. 把網址填入 `src/feedback-config.ts` 的 `FEEDBACK_ENDPOINT`，依一般流程發布。網址是公開的接收位址，不是密碼；接收端只接受本程式的格式、限制大小與筆數，並把以 `=`、`+`、`-`、`@` 開頭的文字轉成純文字，避免被當成公式。
4. 試算表會自動建立「送出紀錄」（每次一列：時間、版本、門市編號、策略、各類筆數）與「明細」（每筆名稱修正、欄位修改、未修改即確認、手動排除一列）。定期以「類型」篩選「明細」：同樣的名稱修正反覆出現代表清理規則要補；同一種提示常被原樣確認代表提示可能是誤報；排除理由重複出現代表可改為自動判斷。
5. 之後若修改接收端程式，須在 Apps Script「管理部署作業」更新同一個部署的版本，網址才會維持不變。

## 格式判斷與擷取

**來源自動分流（逐頁）**：系統直接列印的 PDF（如 Bullzip 等虛擬印表機）帶有真正的文字層，會直接讀取文字，代號、名稱、儲位與帳量不經 OCR，也不載入辨識模型；橫向列印的頁面會自動轉正，表格以小計／頁尾行為結束。頁面只要含有任何圖片（掃描檔，包括掃描器附加的隱藏 OCR 文字）或讀不到表頭，就改用下方的 OCR 流程。手動指定方向重試一律使用 OCR。文字頁在頁面選單標示「PDF 文字」。

**掃描檔的數字辨識**：掃描 PDF 直接取出內嵌原圖，以原解析度辨識（不放大，最長邊上限 4000 px），避免重新渲染再縮放。表頭整行被自動分段漏掉時，會再以稀疏文字模式找表頭字。每列的代號與庫存量另外逐格裁切、放大並黑白化，以三種方式重讀（同一欄的格子疊成一張圖，每種方式只辨識一次），連同兩次整欄辨識共五票投票：三票以上一致且沒有第二個候選有兩票，就自動採用；否則採用最多票的值並列出候選，標為「多次辨識不一致」，須逐筆確認。逐格辨識不允許小數點，避免千分位逗號誤讀成小數點。沒有名稱也沒有庫存量的短數字（如「庫別: 0026」）不會成為商品列。名稱與儲位的辨識分數只在低分時有意義（實測兩份掃描 83 筆：名稱低於 60 分 36 筆中 35 筆確實有誤），因此只有名稱低於 60、儲位低於 40 才提示「辨識品質差」並將欄位標色；其餘仍需逐列確認。

**解析度確認**：匯入掃描檔時會估算解析度（PDF 依內嵌圖片與頁面尺寸計算；JPG/PNG 以整張 A4 估算），低於 300 dpi 會先說明錯誤率較高並詢問是否繼續；取消則不開始辨識。系統列印的 PDF 不檢查。

依「商品代號、名稱、國際條碼、儲位、庫存量」五個表頭的相對位置與六位商品列判斷，店名不是表格辨識條件，只用於輸出標題與多份檔案的同門市確認（比對時忽略空白、全半形與日期時間）。表頭 OCR 有缺字時，會對同一表頭列重做窄帶辨識，依序嘗試單行、區塊與稀疏文字模式。各次辨識分開保留，再取有效表頭；重試不會覆蓋先前辨識正確的欄名。所有必要表頭仍須存在、由左至右排列並位於同一列。續頁可沿用已接受頁面的欄位位置，但仍需符合列結構與報表／前綴特徵；混入其他報表會阻擋輸出。

代號以字串保留前導零，不合併同碼不同儲位。帳量取庫存量，不取寄庫量。文字層會依原始 text run 分欄，避免把同一個 run 截成相鄰欄位；OCR 對帳量採用最後一個足夠寬的字距分開欄位，絕不跨空白拼接數字。兩種頁面分割／數字字元設定互相比對；不一致、缺值、低信心、疑似千分位與前綴疑義均提示人工確認。名稱只從開頭逐段清除已知狀態（停供、不售、換包、冷藏、避光、近效、缺貨、自費、客訂、追禁售、公費、限店等）、`C-` 標記與其短標籤（如 `(紅)`、`(贈藥)`，後接 `&` 亦可辨識）及包裝規格；名稱尾端另移除完整的 `-高健保`、`-高價藥` 標記（`(管4)-高價藥-診所用` 留下 `(管4)-診所用`），其他尾綴不動。包裝／內包裝可含全半形單或雙斜線，單位另涵蓋封、捆、聯、徘；狀態後的連字號、`C-` 後的 `&` 與標籤後的 `&` 均視為前綴語法。`C-` 被 OCR 讀成 `(-`、`-` 等且後接包裝或標籤時依格式移除並提示確認，`C-` 前未知的中文狀態字移除並提示確認；殘留的中文加 `A-`／`B-`／`C-` 標記會留在安全網中提示確認，沒有狀態字的單獨 `C-` 保留並標為疑義。與中文相鄰的 OCR 空白會移除，英文字詞與數字之間的空白保留。第一次代號辨識漏讀的列會由第二次辨識補回並標示，同列出現多個代號或庫存量會標為疑似合併。

來源保留頁碼、欄位座標、原名稱與信心。末筆商品已辨識出的連續跨行名稱會接回同筆，帳量維持原欄位範圍，並排除頁尾／總計文字。校對畫面只建立選中頁的商品列。後續頁與不同方向頁可透過原圖檢視及方向重試；若首張完全無法辨識，應改用較清楚的來源重新匯入。

## 印刷

有資料時效警語或日期未讀取提醒時，僅第一頁表頭上方會以加大粗體紅字印出完整訊息；第一頁表格下移騰出空間，後續頁恢復一般表格高度。以下每頁列數為沒有警語、名稱未增加列高時的配置。

A4 210 × 297 mm、留白 10 mm；五欄寬 40 / 60 / 22 / 25 / 43 mm。表格區由距下緣 264 mm 至 15 mm（249 mm），預設 22.6 mm 列高每頁 11 列（25.8 mm 為 9 列、29 mm 為 8 列；名稱換行增高的列會減少該頁列數）；標題頂端距上緣約 10 mm、頁尾基線距下緣 8 mm，仍避開一般印表機 3–5 mm 的不可列印邊界。Code 128C 含開始碼、校驗碼、停止碼，六位資料共 68 模組；X = 0.4 mm、線高 10 mm，置中後左右留白各 6.4 mm（16X）。為保留條碼高度與 16 pt 六位代碼，範本的各垂直留白縮小 20%：預設列高 22.6 mm、條碼黑線間距 12.6 mm；列頂至條碼 2.4 mm、條碼至代碼約 1.0 mm、代碼至列線約 2.2 mm，下一列條碼前再留 2.4 mm。代碼底部至下一列條碼約 4.6 mm；選擇較高列高時，下方留白隨之增加。

原代號另印於條碼下，使用 16 pt Courier。實量欄 43 mm 完全留白，可手寫九位數。名稱 16 pt、帳量以 Courier-Bold 20 pt（數字過長放不下時才縮小到剛好放入，不拆行）、儲位 10 pt；負數帳量的品項一律排在正數之前，兩組各自依所選規則排序；依儲位排序時，儲位空白的品項在各組內排在最後；名稱依字詞換行（不拆開 `3ML`、`(管4)` 等單位與短括號），可增加列高，整筆不跨頁。第二、四等交錯列從名稱欄延伸至實量欄套淡綠網底，條碼欄維持白底。每頁保留標題、欄名與頁碼；門市、日期、排序方式與來源說明僅第一頁印出，來源說明包含來源檔名（多份時為第一份檔名與檔案數）、筆數、刪除重複筆數與校對版本，不印略過零帳量筆數，頁尾不再印原尺寸、最低列高及手寫提醒。來源說明對應產生當下凍結的校對資料，資料或設定一改，舊 PDF 即失效無法下載。

網頁預覽以正確編碼後的 Libre Barcode 128 字型顯示；PDF 使用同一 Code 128C 編碼的向量線條。PDF 內完整嵌入靜態 Noto Sans TC 400 字型（fontkit 子集化 CJK 時文字層正常但字形顯示空白，已於 2026-10-10 以靜態字型重測確認），每份約 4.4 MB；關閉 `locl` 以避免中文段落內數字替換影響文字複製。使用者不需安裝字型。

## 開發與重現

Node.js 22.13+；`npm ci`、`npm test`、`npm run build`、`npm run dev`。

先執行 `npm run audit:source` 檢查 tracked source、敏感路徑、憑證模式與公開依賴 SHA-256，再執行測試、建置及 `npm run audit:dist`。`.gitattributes` 固定程式的 LF 換行；公開依賴以原始 bytes 保存，確保 Windows/Linux 的資源雜湊一致。

GitHub Actions 在 push main、pull request 與手動執行時，測試 Ubuntu Node 22/24 及 Windows Node 22；包括 `npm ci`、source audit、單元測試、TypeScript/Vite build、dist audit，並保存 Ubuntu Node 22 的靜態 build artifact 七天。私有原檔測試在未提供本機原檔時明確跳過，CI 通過不代表門市實機或原檔 OCR 驗收。

程式結構、已重現問題與簡化順序見 [2026-10-21 程式 review](docs/code-review-2026-10-21.md)。

健保用藥品項精簡檔（比對商品代號與健保藥品代號、以及處方警示對照 ATC 用的參考資料；網站程式不直接讀取，處方警示用的 `public/assets/rx/drugs.json` 由它產生）見 [docs/reference/nhi-drug-codes.md](docs/reference/nhi-drug-codes.md)。

ICD-10-CM 中英文對照檔（健保署 2023 年版中文版，處方警示以中文顯示診斷碼用的參考資料；網站程式不直接讀取，`public/assets/rx/icd10cm.json` 由它產生）見 [docs/reference/icd10cm-zh.md](docs/reference/icd10cm-zh.md)。

商品代號（六碼）對健保藥品代號的比對、查表工具 `npm run nhi-map`（網站程式不讀取），見 [docs/reference/sku-nhi-map.md](docs/reference/sku-nhi-map.md)。對照檔本身含整個商品檔的六碼與品名，放在另一個 private repo，不放在這裡；以 `--map` 或環境變數 `SKU_NHI_MAP` 指定。

## GitHub Pages 自動發布

`.github/workflows/pages.yml` 在 main 的「Build and test」push 執行成功後，對同一 commit 重跑 source audit、測試、以 `--base=/GTsloth-s-eye/` 建置及 dist audit，再部署到 GitHub Pages；也可在 Actions 頁手動執行（僅限 main）。發布使用 GitHub 內建的 `GITHUB_TOKEN` 與 OIDC。

首次啟用（只需一次）：

1. 儲存庫已改為 public（私有儲存庫的 Pages 需要 GitHub Pro／Team 等付費方案）。repo 內沒有私有 PDF 或 credentials，source/dist audit 會擋下禁止路徑與憑證樣式；新增檔案時仍須維持這個前提。
2. Settings → Pages → Build and deployment → Source 選 **GitHub Actions**。
3. Actions → Deploy GitHub Pages → Run workflow（branch: main），之後每次 main CI 通過都會自動部署。

尚未啟用 Pages 時，workflow 只留下警告並略過部署，不會讓 main 變紅。

## 版本更新

1. 從 GitHub main 建立修訂分支，修改 source；發布前以 `npm version patch --no-git-tag-version`（或適當的 minor/major）同步 package.json 與 lockfile。網頁頁尾版本直接由 package.json 產生。
2. 完成 source audit、測試、建置及 dist audit 後提交、push，透過 pull request 合併至 main。
3. 確認該 commit 的「Build and test」與「Deploy GitHub Pages」執行成功，再核對公開網站的頁尾版本。

`public/assets/manifest.json` 記錄依賴版本、來源、SHA-256 和授權；`scripts/assets.mjs` 可重下載公開資源。完成後使用 Python 與 `fonttools==4.60.1` 執行 `scripts/static-font.py` 產生 PDF 靜態字型，再執行 `npm run slip-assets` 補回領藥憑單底圖與醫院名冊的紀錄、`npm run rx-assets` 補回處方警示資料的紀錄。一般建置不需重新下載資源。完整授權位於 `public/assets/licenses/`。

`qa.html` 與 `scripts/browser-qa.ts` 是本機開發驗證入口，不包含於 Vite 正式輸出。其大量 PDF 功能專供效能測試，不執行人工確認；正式網站的校對關卡始終有效。

私有人工基準存在本機 `tests/fixtures/sample-gold.json`。原範本未隨來源庫發布，缺少該基準時對應測試會明確跳過。`scripts/qa-fixtures.py` 需要原檔，製作 200 頁、續頁、混合文件與超頁數樣本；`scripts/qa.ts` 產生校對基準 PDF；`scripts/verify-pdf.py` 使用 PyMuPDF、Pillow、ZXing C++ 3.1.1 獨立驗證 PDF 與條碼。

實際印表機／掃描器驗收仍需門市設備。先列印三種間距測試頁，逐列確認代號及前導零；若掃到相鄰列，增加列高再測。
