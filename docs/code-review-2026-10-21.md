# 程式 review 與簡化建議

日期：2026-10-21。檢查基準：`5b3f082`，另包含本次發布設定與文件清理、後續新增的盤點資料時效提醒。以下管理頁功能問題與重構建議尚未套用修正。

## 專案目的與既有分工

這是門市報表的瀏覽器工具集，首頁提供工具入口。盤點工具接受文字 PDF、掃描 PDF 與圖片，經校對後輸出條碼盤點表；管理工具只接受系統列印的文字 PDF，以庫存簡表和調劑統計產生安全量、呆藥與空位清單。報表處理留在當次頁面記憶體；管理工具另外送出有限的校對回饋。

`model`／`management-model` 負責資料規則，`parser`／`textlayer`／`management-parser` 負責解析，`pdf`／`management-pdf` 負責列印，兩個頁面入口負責互動與生命週期。名稱清理與文字解析已有共用，管理規則也已集中為可獨立測試的函式。

## 功能問題與日期處理政策

### 1. 日期差異應依分天列印的作業情境處理

位置：`src/management-parser.ts:89–90`；比對端為 `src/management-report.ts` 的 `derive()`。

調劑頁解析出了 `facts.printed`，但跨頁比對用的 `meta` 只包含門市、期間、給付方式與總頁數。庫存頁的 `meta` 有列印日期，因此庫存簡表自己的各頁日期不同時會阻擋，調劑表則接受。兩種報表彼此的列印日期不同，目前可以匯入；庫存日期早於調劑截止日僅提示。

驗證：用合成文字頁建立同一檔案的第 1、2 頁，日期分別為 2026/10/16、2026/10/20。解析結果的日期不同，但 `meta` 相同；搭配有效庫存頁呼叫 `derive()`，得到 `blockers: []`、`ready: true`。

使用者補充：人工作業排程會使報表分天列印。因此上述結果不能單憑日期不同就判為缺陷，原先列為 P2 並建議直接阻擋過於嚴格。統計期間與篩選條件固定、資料沒有回補或修正時，不同日列印也可以得到相同結果。風險在於兩次列印之間資料已改變，部分頁面可能來自不同快照，造成加總、排名或建議量失真；日期只能提示這個可能性，無法證明資料不同。

修訂建議：日期差異可顯示分天列印提示，與門市、期間、給付方式、缺頁及同頁內容衝突的阻擋條件分開。來源核對與過期警語目前只採第一頁日期，可考慮顯示日期範圍並依最舊頁提醒。若要放寬庫存簡表的跨頁日期限制，也須同步更新 README 與回歸測試；管理報表的日期接受規則尚未調整。

後續實作（v1.2.5）：依使用者要求，盤點輸出區與 PDF 每頁新增列印日距台灣今日 3 天（含）的警語，取所有來源頁最早日期，包含零庫存或已去重的頁面；日期讀不到時提示人工核對。文字 PDF 直接取日期，掃描檔辨識頁尾。PDF 快取跨日會更新警語，日期工具與管理共用；管理維持 7 天（含）門檻，其跨頁日期接受規則維持既有行為。

### 2. [P2] 管理頁重新產生 PDF 會留下未釋放的 Blob URL

位置：`src/management.ts:355–369`，尤其是 `outputs = results`。

每次按「產生勾選的 PDF」都建立新 Blob URL，再直接覆蓋 `outputs`。沒有資料變更時仍可重按產生，舊網址不會經過 `invalidate()`，之後也無法釋放。若一批中第二份產生失敗，先完成的第一份網址同樣沒有清除。PDF 完整嵌入中文字型，單份約 4.4 MB，重複操作會持續保留記憶體。

驗證：直接擷取現有 `generate()`，以替身取代 PDF 產生、字型與回饋傳送，追蹤網址生命週期。連續產生兩批、每批三份，得到 6 個存活網址，但 `outputs` 只保留 3 個；模擬清除目前輸出後仍剩 3 個。此驗證沒有對外傳送資料。

建議：集中管理輸出網址；成功替換前釋放上一批，失敗或校對版本變動時釋放尚未交付的整批。回歸測試應涵蓋連續產生、第二份失敗，以及產生期間資料變更。

## 可簡化的重複工作

### 3. 庫存文字頁重算兩次字元座標

`src/management-parser.ts:125` 已呼叫 `textLayer(text)`，`parseStockPage()` 卻再呼叫 `extractTextPage(filePage, text)`，後者在 `src/textlayer.ts:78` 再做一次 `textLayer(text)`。每頁都重複字元展開、旋轉與分行，管理工具可匯入數百頁時尤其沒有必要。

建議：抽出接受既有 `TextLayer` 的擷取函式，盤點保留從 `TextPage` 進入的薄包裝，管理直接重用算好的 layer。這樣仍共用同一套庫存列解析規則。

### 4. PDF 共用函式帶入不必要的依賴

`src/management-pdf.ts:5` 為了 `mm` 與 `wrapText` 匯入整個盤點 PDF 模組，後者另載入 JsBarcode。兩個 PDF 產生器也各自複製 fontkit 註冊及中文字型嵌入設定。

實際以 Pages 子路徑建置後，管理頁預載入的共用 JS 約 1,653 kB，內含 Code 128 程式；這是整個共用 chunk 的大小，不能全歸因於條碼。首頁仍只有輕量入口，沒有載入這個 chunk。

建議：把單位轉換、換行及字型設定移到獨立共用模組；條碼留在盤點模組；PDF 產生器可在需要輸出時才動態匯入。建置前後應比較入口依賴與壓縮大小，並確認中文、條碼及列印版面。

### 5. 畫面重繪與資料重算可以分開

`src/management.ts` 的 `render()` 每次都重跑 `derive()`，校對翻頁與勾選輸出清單也會重新聚合、排序整份資料。合作診所模式的 `derive()` 另呼叫兩次 `safetyList()`；預覽中 `listRows()` 又會被卡片、`listSpec()` 與部分 `listAlerts()` 重複呼叫。

建議：在來源、列資料或策略改變時更新衍生資料；校對翻頁、預覽開關與勾選清單重用現有結果。同一次 render 共用已整理的列資料。先量測大份報表的重算時間，再決定是否拆分安全量計算的排名與係數階段。

### 6. 少量修改殘留可順手清理

額外執行 `tsc --noEmit --noUnusedLocals --noUnusedParameters` 找到 5 個診斷：`scripts/browser-qa.ts` 的 `i`、盤點入口只寫不讀的 `errorMessage`、管理解析器的 `Origin` 與 `code`、管理報表的 `PARTNER_LIMIT` 匯入。一般建置未啟用這兩個 unused 選項，因此目前正常通過。

`management-model.ts` 另有過時註解：`LONG_PERIOD` 註解仍包含空位清單、`coefficient()` 註解仍稱預設為倉鼠派；實際空位判斷已不受期間限制，預設策略已是平衡派。這些應與程式一併校正。

## 建議保留的複雜度

- 精確分數與日曆月計算有整數邊界測試，能避免安全量多進位一單位。
- OCR 多次讀取與投票有明確的誤辨來源；文字 PDF 已走直接解析與模型延遲載入。
- 跨檔去重的 `sourceFiles` 保留每份原報表內的重複列；現有測試涵蓋先讀各檔首頁的順序。
- PDF 全字型嵌入有中文字形空白的既有驗證依據，調整前需重新檢查實際顯示。
- CI 的跨平台矩陣有驗證用途。Pages 再建置是因 CI artifact 使用根路徑，而正式站使用 repo 子路徑；若要共用 artifact，應先統一 base 與來源 commit 的關聯。

## 驗證與範圍

- `npm test`：115 個測試，107 通過、8 跳過、0 失敗；跳過項目需要私有來源檔。
- `npm run audit:source` 通過。
- `npm run build -- --base=/GTsloth-s-eye/` 通過；有上述共用 chunk 超過 1,500 kB 的提示。
- `npm run audit:dist` 通過，216 個公開資源 SHA-256 均符合 manifest。
- 跨頁日期接受行為與 PDF 網址生命週期以合成資料及函式替身驗證；日期差異依上述作業情境不列為已確認缺陷。未執行門市私有原檔 OCR、實體列印或掃描器驗收。
- Chromium 實測盤點文字 PDF：兩天前、三天前、多檔混合與缺少日期；下載後逐頁核對警語與全部六碼。模擬台灣跨日後由預覽對話框重新下載，也會更新日期與警語。合成掃描圖片另經實際 Tesseract 辨識，成功讀到頁尾日期並提醒。

建議順序：先修正 PDF 網址生命週期，再處理重複文字轉換、PDF 依賴及重繪時重算；日期提示與接受規則依分天列印的作業需求整理，未使用符號與過時註解可獨立清理。
