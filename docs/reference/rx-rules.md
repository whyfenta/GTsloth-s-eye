# 處方警示規則表（草稿）

> **狀態：藥師審核中。** 規則表由先前的開發 session 憑藥學知識起草，尚未逐條對照仿單。「依據」欄（仿單、指引、常見、常見仿單外）是起草者的判斷，不是查證過的結果；引用的準則與指引、各自的版本與確認日期列在 [`rx-sources.md`](rx-sources.md)。藥師已審過第一批（見下方「藥師審核」）；115/11/11 時 233 條裡 130 條已結案、103 條待審（含 115/11/10 依第一份週檢查加入的 26 條），以審核頁（`review/`）為準。審完第一批後網站的處方警示改為預設開啟，未審的規則照原樣生效、陸續審核；開關見 README「處方警示」。

檔案：[`rx-rules/`](rx-rules/) 底下 6 個 CSV，UTF-8（含 BOM）。前 5 個（適應症、同處方、注意事項、科別、藥品分類）從規則草稿資料夾原樣複製；`settings.csv` 是這次新增的，把需要藥師決定的做法從程式移到表格。

用途：`npm run rx-assets` 逐列檢查後轉成 `public/assets/rx/rules.json`，由 `src/rx-check.ts` 判定。判定邏輯照規則草稿的 Python 原型 `check_rules.py`（不在 repo 裡），兩者對每個藥的判定以本機樣本比對一致，見下方「試跑與比對」。

## 判定方式

每個藥依序判定，前一層解釋得了就停：

1. **適應症**（`indications.csv`）：本次的某個診斷碼可以解釋這個藥。同一個藥對到多列時，依「依據」先試仿單、再指引、常見、常見仿單外，其他寫法最後；同一種依據照檔案順序。
2. **同處方**（`co-drugs.csv`）：同一張處方上的另一個藥可以解釋它，例如抗血小板藥解釋胃藥。同一個健保碼開兩次不算。網頁仍把這類藥列為灰色提示（藥師審核：因別的藥而開的藥也要提示，但不必到黃色）。
3. **科別常用**（`specialty.csv`）：QR 第 7 欄的就醫科別常開這類藥。`settings.csv` 可以停用這一層。
4. **低風險**（`drug-classes.csv` 類型「低風險」）：不提示。
5. 都解釋不了：高警訊藥（`drug-classes.csv` 類型「高警訊」）給黃色，其他給灰色。處方沒有診斷碼時一律灰色。

另外：

- **注意事項**（`cautions.csv`）：不論上面判定的結果，每個藥都另外比對。藥品以 ATC 或成分關鍵字對上後，看條件：診斷（本次有這些診斷碼）、年齡（年齡層至少幾歲或未滿幾歲）、性別（QR 第 5 欄身分證字號的第 2 碼：身分證 1 男、2 女；統一證號新式 8 男、9 女，舊式 A、C 男，B、D 女）、同處方（同一張處方有這些 ATC 的藥，可限定那個藥的頻率）。一條可以有多種條件，全部成立才提示；有一種不成立就不提示；其餘成立、但有一種無法判斷時給灰色：年齡層跨過門檻時「無法判斷」，沒有生日或生日格式認不得時「無法讀取年齡」，第 2 碼不是上述字元（或沒有字號）時「無法取得性別資料」。
- **較具體的注意事項取代較一般的**：同一個藥同時對到兩條注意事項，若兩條的 ATC 與成分關鍵字寫得一樣，而一條的條件包含另一條的全部條件還多幾項，只顯示條件多的那條。例如 C17 是 C09（65 歲以上用 BZD，灰色）再加上同處方有 α 阻斷劑或睡前降血壓藥，成立時只顯示黃色的 C17，這就是 C09「升一級」。
- **同成分重複**：同一張處方兩個以上不同健保碼含相同成分時提示，等級在 `settings.csv`。成分名去掉含量（MG、MCG、G、ML、IU、U、%）、括號與鹽類字尾（HCL、SODIUM 等）後比對，所以 INSULIN GLARGINE 和 INSULIN ASPART 仍是兩個成分。
- **沒有診斷碼的處方**：整張只給一則灰色提示，不對每個藥逐一提醒；注意事項照常比對。
- **不在健保用藥品項的代碼**（例如特材）：當成低風險，也不比對注意事項。已知的特材寫在 `src/rx-check.ts` 的 `SUPPLIES`，畫面顯示名稱、週檢查資料不列為「查無藥品碼」：目前只有 `NAN02A1000ZZ` 胰島素注射針頭（各種規格都用這個碼；藥師說明 115/11/10），它不與任何藥品或診斷衝突，但有胰島素卻沒有針頭時 C67 提示。
- 診斷碼比對前，QR 與規則兩邊都去掉小數點並轉成大寫。
- **同一病人的多張處方合併比對**（憑單畫面）：同一病人（身分證字號相同；讀不到字號時姓名與生日都相同）同時交付的多張處方，把全部的診斷與全部的藥品當成一張來判定（`checkPrescriptions`）：適應症、注意事項的診斷條件看全部的診斷；同處方解釋與注意事項的同處方條件看全部的藥（先找同一張上的藥）；同成分重複也跨張計算，同一個健保碼開在兩張處方算重複（同一張上開兩次不算）。科別常用只看藥品自己那張處方的科別；年齡層與性別取第一張有資料的。理由用到別張處方的診斷或藥時，前面標出「第 n 張」，別張的藥以「併用：」開頭、同一張的照舊寫「同處方：」。只有一張處方時結果與原本完全相同，原型比對與處方樣本的判定摘要（每一行單獨計算）都不受影響；處方樣本另以「合併多出」記下合併才多出的注意事項編號（見 README「處方樣本」）。

## 寫法

- 一格有多個值時以半形空格分隔。
- **ATC**：寫前綴，例如 `C`（所有心血管藥）、`C10`、`C10AA`、`C10AA05`。
- **ICD-10-CM**：寫前綴，例如 `E11`、`N18.4`；或寫範圍，例如 `I10-I16`。範圍兩端的碼長要相同、前小後大，比對時取診斷碼的前幾碼（與範圍兩端同長）落在兩端之間，所以 `I20-I25` 包含 `I25.10`、不包含 `I26`。
- 等級只能是 `紅`、`黃`、`灰`。
- **注意事項的條件**：`條件類型` 寫 `診斷`、`年齡`、`性別`、`同處方` 之一，多種時以 `+` 連接，例如 `年齡+同處方`；`條件` 依同樣順序寫成以 `;` 分隔的幾段，例如 `>=65;G04CA C02CA`。年齡寫 `>=65`（65 歲以上）或 `<50`（未滿 50 歲）；性別寫 `男` 或 `女`；同處方的 ATC 後面加 `@HS` 表示那個藥的頻率含 HS 才算（HS、QHS、HSPRN、QD&HS 等），例如 `C08@HS`。
- **後來加的三種條件（115/11/10）**：
  - `未同處方`：同處方（合併比對時含其他張）沒有這些藥才成立。寫 ATC 前綴，或 `=健保碼` 指定一個沒有 ATC 的特材，例如 C67 的 `=NAN02A1000ZZ`（胰島素注射針頭）。
  - `同類數`：寫成 `>=3 N05A N05B …`，同處方有至少幾種不同健保碼的藥（這個藥本身也算）屬於這些 ATC 才成立；同一張只在第一個算到的藥提示一次，避免每個藥都重複一則。
  - `腎功能`：寫成 `<30`（eGFR，mL/min/1.73 m²）。依診斷的 CKD 分期判斷：N18.1 ≥90、N18.2 60–89、N18.3／N18.30 30–59、N18.31 45–59、N18.32 30–44、N18.4 15–29、N18.5、N18.6 與 Z99.2（透析）<15、N18.9（未分期）0–89；有多個分期時取最差的。範圍整個低於門檻才成立，跨過門檻時給灰色「腎功能無法判斷」。沒有 CKD 分期時，以年齡與性別粗估（下方「腎功能粗估」），粗估低於門檻時也只給灰色問句，從不給黃、紅。

## 各檔欄位

| 檔案 | 欄位 |
|---|---|
| `indications.csv` 適應症 | ATC、藥理類別（說明用）、可解釋的ICD-10、依據、備註（說明用） |
| `co-drugs.csv` 同處方 | ATC、可由同處方的ATC解釋、依據、備註（顯示在理由裡） |
| `cautions.csv` 注意事項 | 編號、ATC、成分關鍵字（大寫，比對健保成分）、條件類型（診斷／年齡／性別／同處方／未同處方／同類數／腎功能，多種以 `+` 連接）、條件（診斷碼、`>=65`、`<50`、`男`／`女`、ATC、`=健保碼`、`>=3 ATC…` 或 `<30`，多段以 `;` 分隔）、等級、提示（顯示的文字）、依據（說明用） |
| `specialty.csv` 科別常用 | 科別代碼（健保就醫科別 2 碼）、科別（說明用）、該科常開的ATC |
| `drug-classes.csv` 藥品分類 | ATC、類型（低風險／高警訊）、說明（說明用） |
| `settings.csv` 設定 | 設定、值、可選的值、說明。`同成分重複`：紅／黃／灰；`科別常用`：保留／停用 |

## 修改流程

1. 改 CSV。表頭不要動；用 Excel 編輯時另存成「CSV UTF-8」。新增藥品清單時，用 `nhi-drug-codes.csv` 的成分核對每個 ATC：前綴可能多抓（`G04BD` 含 β3 促效劑 mirabegron），ATC 也可能標錯（A04AD01 唯一的品項其實是 butylscopolamine）。
2. 執行 `npm run rx-assets`。格式不對時會停下，並指出哪個檔、第幾列、哪一欄。
3. 執行 `npm run rx-review-page -- 樣本…`（見下方「審核頁」）。它更新審核紀錄 `rx-rules-review.json` 與審核頁讀的清單 `public/assets/rx/review.json`；發布後，新條文和改過內容的規則會出現在藥師團隊的待審。
4. 執行 `npm test`。`public/assets/rx/rules.json` 沒有重產、審核紀錄或審核頁清單沒有更新、或注意事項的依據沒有對到 `rx-sources.csv` 的來源時，測試會失敗。
5. 有本機樣本時，可另外跑和原型的比對（見下方）。比對只看邏輯：原型會改用 repo 裡的規則表，所以改規則不會讓比對失敗；但 `settings.csv` 要是原型的做法（同成分重複＝黃、科別常用＝保留）。
6. 照一般流程開 PR。

## 試跑與比對

規則起草時，用同事以收集頁（`collect/`）收來的 171 張去識別化處方試跑：558 個藥品，14 張處方（8%）出現黃色警示，沒有紅色。規則是照這批樣本調的，所以 8% 偏樂觀；同事會再收 100～200 張新樣本驗證。樣本與試跑結果都留在本機，不放進 repo。

**第一次驗證（115/10/31）**：用 94 張起草時沒看過的新樣本，在規則未調整的情況下試跑：282 個藥品，5 張處方（5%）出現黃色警示，沒有紅色。其中 3 張是值得確認的警示（NSAID 加十二指腸潰瘍；amlodipine 單方加含 amlodipine 的複方，2 張），2 張是規則缺口：免疫抑制劑配器官移植（Z94.4），以及含心衰竭的合併碼 I11.0。依這批樣本補上：calcineurin 抑制劑（L04AD）、心衰竭合併碼（I11.0 I13.0 I13.2）、硝酸鹽類與 nicorandil（C01D）、ATC 歸在 N02BA01 的 aspirin，以及皮膚科（科別常用、acitretin、外用 calcineurin 抑制劑）。補過之後這批也算看過了，下次驗證要再收新樣本。

**持續收集（115/11 起）**：憑單模式列印時自動送出去識別化樣本，每週一整理成「驗證用」裡的 `處方QR去識別化_自動_*.txt` 與「每週檢查」的週檢查資料，再由排程的 Claude 寫審閱報告（流程見 README「處方樣本試算表」與 [`../rx-samples-weekly-review.md`](../rx-samples-weekly-review.md)）；報告除了檢討出現的警示，也逐張找規則沒抓到的問題（`rx-try --detail`），並用累計的匯出檔看每條注意事項的覆蓋度（`rx-try --coverage`）。審閱只提建議；要採用的修改照上方「修改流程」處理，可以先用 `npm run rx-try -- 樣本.txt` 比較修改前後哪些處方的判定改變。用來調整過的樣本移到「已用於調整」。統一證號的性別從 115/11 起才判讀（之前第 2 碼是 8、9、A～D 的樣本第 5 欄都是空白）。

**第二次驗證（115/11/05）**：用同事新收的 97 張（和先前 265 張沒有重複），在規則未調整的情況下試跑：269 個藥品，8 張處方（8.2%）出現黃色警示，沒有紅色。其中 7 張是值得確認的警示：BZD 配 α 阻斷劑或睡前降血壓藥（C17，2 張）、BZD 配失智症（C42，2 張，其中 1 張同時有抗精神病藥配失智症 C10）、沒有糖尿病診斷卻開 metformin（2 張）、methylphenidate 長效加短效（同成分重複）。另外 1 張是皮膚科 azathioprine 的規則缺口。C18、C19–C41、C43 在這批沒有命中。這批多了性別欄（87 張有 SEX 標記）。依這批提出的規則與問題見「藥師審核」的「第二次驗證」；這批也算看過了，放在 Drive 的「已用於調整」。先前 265 張用同一版規則重跑：黃色 23 張（8.7%），沒有紅色。

資料問題：有 3 家院所的生日是 6 碼（`AGE?999999`，362 張裡共 8 張），讀不到年齡，年齡條件的注意事項都只能給灰色「無法讀取年齡」；去識別化後看不出是哪種格式，要看一張原始 QR 才能修。有 1 家院所用院內 3 碼科別（`010`、`003`、`0D6` 等），都當作未知科別。這批有 4 家院所的第 5 欄沒有性別標記（共 10 張），性別條件的注意事項會給灰色。

`tests/rx-check-samples.test.ts` 用這批樣本確認 TypeScript 版和原型對每個藥的判定、理由、注意事項，以及診斷碼的中文名稱都一致（目前 362 張全部一致）。沒設環境變數時跳過：

```bash
RX_SAMPLES="樣本1.txt;樣本2.txt" RX_PROTOTYPE=../rx-rules-draft/check_rules.py npm test
```

`RX_SAMPLES` 的多個檔案在 Windows 以 `;`、其他系統以 `:` 分隔。測試只印出張數與不一致的樣本行號，不印樣本內容。

## 藥師審核

藥師團隊在審核頁逐條看規則（每條附依據、樣本中的命中次數，ATC 碼附中文類別、成分與商品名），選同意、不同意或其他意見；每週檢查的提案也在同一頁表決。這裡只記錄決定與改了什麼。

### 審核頁

審核頁是網站的 `review/`（https://whyfenta.github.io/GTsloth-s-eye/review/ ，不在首頁導覽）。藥師團隊用負責人分享的連結（網址後面帶團隊代碼 `?code=…`）開啟，填名字後逐條選同意、不同意或其他意見；決定存在試算表「GTsloth 規則審核（團隊）」，彼此看得到。設定見 README「規則審核頁」。115/11/11 以前的審核頁是 claude.ai 上的私人 Artifact「處方警示規則審核」，只有負責人能存；當時的決定已經寫進審核紀錄（115 條同意結案，3 條只有意見的列在該條的提醒裡），那一頁不再更新。

頁面讀三樣東西：

- **規則清單** `public/assets/rx/review.json`：`npm run rx-review-page` 產生，跟著網站發布。內容是每條規則的中文藥名與診斷名、依據、提出原因、樣本中的命中次數（只有次數）與審核是否結案。它和審核紀錄一樣是公開的，不含樣本內容與審核者姓名。
- **團隊的決定**：試算表的「票」分頁，一位審核者對一個項目一列；「統計」分頁是每個項目幾位同意、不同意、其他意見與意見內容，給負責人和 Claude 讀。AI 預審的意見只在「AI 預審（不計票）」欄，不在前面的計數與意見裡。
- **提案**：每週檢查與每月的依據來源確認留在 Drive「每週檢查」的提案表（「週檢查_日期（提案）」「指引確認_日期（提案）」）。提案是還沒進規則表的建議，審核者選採用、不採用或需更多樣本。頁面從兩個地方讀提案，合在一起顯示：隨網站發布的 `public/assets/rx/proposals.json`（`npm run rx-proposals -- --publish 提案表.csv …` 產生），以及試算表的指令碼當下從 Drive 讀到的提案表。指令碼讀不到 Drive 時（例如沒有雲端硬碟權限），已發布的提案照樣看得到，只有還沒發布的最新一週要等。

怎麼算審完：

- **達門檻**：同意的人數達到門檻（預設 2 位，試算表指令碼屬性 `QUORUM`），而且沒有人不同意或有其他意見。
- **有分歧**：只要有一位不同意或有其他意見，由負責人看過意見後決定。
- **AI 預審不計票**：名字含「預審」的審核者（排程的 Codex）是 AI 預審，不是藥師簽核：它的決定不算進門檻、不造成分歧，頁面另列在每條下方。結案時可以參考它查到的出處，但 `approved` 的同意人數只算藥師（115/11/13 起；先前 Codex 的 2 筆意見曾讓 P20261111-01、-02 顯示為有分歧）。
- 達門檻或有分歧都不會自動改任何東西。**結案**是負責人請 Claude 做的事，寫進審核紀錄 `rx-rules-review.json`：照原樣保留的記 `approved`（結案日期與同意人數），依意見修改的記 `outcome`（處理結果）。頁面上結案的項目不再出現在待審。
- 決定的時間早於規則的最後改變時間，就不算：這條回到待審，頁面顯示原本的內容。規則改了內容，先前的 `approved` 也會拿掉。如果改動就是照團隊的意見改的，在 `--notes` 的該條加 `applied`（處理結果），不會回到待審。
- 從規則表拿掉的規則進「已刪除」。

`rx-rules-review.json` 記每條規則的編號、內容指紋、所屬批次、最後改變時間、提出原因與結案結果，以及已結案的提案（`proposals`）。內容指紋只看會改變判定的欄位，改 `備註`、`說明` 不算改規則。適應症等沒有編號的列，編號只看內容，列的順序變了也不會變。它在公開的 repo 裡：說明只寫張數與藥品組合，不寫院所代碼、某張處方的年齡層或審核者姓名（`npm test` 會檢查）。

**規則表有新增或修改時**：執行 `npm run rx-review-page -- 樣本1.txt 樣本2.txt …`，把 `rx-rules-review.json` 與 `public/assets/rx/review.json` 一起 commit。不給樣本時，沒改過的規則沿用上次的命中次數，新增或改過的規則沒有次數。新規則需要說明時，加 `--notes 說明.json`：為什麼提出、出處連結、新問題、ATC 中文名（格式見 `scripts/rx-review-page.ts` 開頭）。

**結案（負責人請 Claude 做）**：

1. 讀試算表「GTsloth 規則審核（團隊）」的「統計」分頁（Google Drive connector），或請負責人在審核頁按「複製團隊統計」貼上。
2. 達門檻的規則：在 `--notes` 的該條寫 `"approved": { "at": "結案日期 YYYY-MM-DD", "n": 同意人數 }`。
3. 有分歧的規則：把意見整理給負責人決定。決定修改的，改規則表並在 `--notes` 的該條寫 `applied`（處理結果，例如「依意見降為灰色」）；決定照原樣的，寫 `approved`，並在 `outcome` 或這份文件記下不採納意見的理由。
4. 提案：把 Drive「每週檢查」裡還有未結案提案的提案表下載成 CSV，執行 `npm run rx-proposals -- --publish 表1.csv 表2.csv …` 更新 `public/assets/rx/proposals.json`（它整份取代，所以每一份都要給）。採用的照上方「修改流程」加進規則表；不論結果，在 `--notes` 的 `proposals` 寫一筆 `{ "id": "P20261116-01", "title": "…", "status": "已採用｜不採用｜需更多樣本", "decided": "YYYY-MM-DD", "note": "…", "rules": ["C78"] }`。依提案原樣加入、而且表決已達門檻的規則，可以同時寫 `approved`，不必再審一次；內容和提案不同的要重新審。每週檢查讀這些紀錄，不會重提已經不採用的提案。
5. 執行 `npm run rx-review-page -- --notes 說明.json`、`npm test`，把決定與改動記在這一節，照一般流程開 PR。

**現有寫法仍做不到的**（報告第 3.10、3.11 節）：劑量（每日量乘成分含量，例如 70 多歲每日 lorazepam 2 mg、rivaroxaban 10 mg 用於心房顫動）、2 種以上抗膽鹼藥的計數（`同類數` 已能寫，但「強抗膽鹼藥」的清單要先審）。

## 持續精進的循環（115/11/11 檢查）

憑單送出去識別化樣本 → Apps Script 每週整理 → 排程的 Claude 寫審閱報告與提案表 → 藥師團隊在審核頁表決 → 負責人請 Claude 修改規則表並結案 → 下一週的檢查追蹤結果。第一輪（115/11/09 的報告、115/11/10 依報告加入 C56–C77）已經實際跑完，檢查時發現並補上的缺口：

- **新規則沒有進審核頁**：115/11/10 的 26 條已經合併生效，但寫進審核頁是另一個手動步驟，當時沒有做。現在清單是網站的一部分（`public/assets/rx/review.json`），規則表改了而清單沒更新時 `npm test` 會失敗。
- **只有負責人一個人能審**：原本的審核頁是私人頁面。改成 `review/` 的公開頁加團隊代碼，多位藥師各自表決，達門檻或有分歧一目了然。
- **建議沒有記憶**：報告裡沒被採用的建議（例如 pentoxifylline 配慢性腎病、含 codeine 的 R05 複方、4 碼院內科別被截成 2 碼、年齡欄的異常寫法）沒有地方追蹤，下一週可能重提或被忘記。現在每週的建議寫成提案表，在審核頁表決，結果記在 `rx-rules-review.json` 的 `proposals`，每週檢查第 3 步追蹤每一項的狀態。
- **沒有跨週的指標**：報告新增「指標」一節，和上一份並列（黃紅比例、紅黃處方中值得確認的比例、失敗率、年齡讀不到的比例、未結案條數）。
