# 處方警示的依據來源

[`rx-sources.csv`](rx-sources.csv) 列出規則引用的準則、指引與主管機關資料：目前依據哪一版、多久確認一次、上次什麼時候確認過、狀態，以及規則的「依據」欄怎麼寫它。UTF-8（含 BOM）。

## 為什麼要有這份清單

115/11/10 盤點 `cautions.csv` 的 76 條注意事項（`npm run rx-sources`）：

- 43 條的依據是仿單（禁忌、警語、黑框警語），31 條是 Beers 2023，6 條是 FDA、3 條是 EMA、2 條是 ESC 指引，6 條是藥師的決定或起草者判斷（一條可以有兩個依據）。
- 仿單那 43 條多數是起草時依藥學知識寫的，沒有逐條對照國內仿單；依據欄自己就寫著「待核對」「未核對」「美國」「英國 SmPC」的有 7 條（C39、C40、C46、C48、C54、C57、C58）。
- 來源寫在每一條的依據欄裡，沒有一個地方記著「我們依據的是哪一版」。Beers 約每 3 年改版（2026 年預定更新），改版時要找出全部 31 條重新核對，只能靠搜尋文字。

所以來源集中列在這裡，規則引用時用清單上的寫法，`npm test` 會檢查。

## 該不該加入其他指引

規則式的處方警示只看得到一張處方上的診斷碼、藥品、年齡層與性別，看不到檢驗值、病史與先前的處方。一個來源能不能變成規則，看它有沒有**明確的「應避免」條文，而且單張處方判斷得了**：

| 類型 | 例子 | 適不適合 | 做法 |
|---|---|---|---|
| 明列應避免藥品的準則 | Beers、STOPP、PIM-Taiwan | 最適合：本來就是設計來逐條檢查的 | Beers 已使用；**建議加入 STOPP/START v3**（只取 STOPP、且 Beers 沒有的條文）與 **PIM-Taiwan**（依國內品項整理） |
| 主管機關的安全資訊 | 仿單、食藥署風險溝通表、FDA、EMA | 適合：禁忌、警語、併用限制都很明確 | 仿單、FDA、EMA 已使用；**建議加入食藥署藥品安全資訊風險溝通表**，每月確認 |
| 治療指引裡的「避免」條文 | 心衰竭指引的避免用藥、GINA 的長效 β2 促效劑單方、糖尿病指引的 GLP-1 促效劑＋DPP-4 抑制劑、心房顫動指引的機械瓣膜不用 DOAC、KDIGO 的慢性腎病避免 NSAID | 部分適合：只取這類條文 | **建議加入**：心衰竭、糖尿病（ADA 與國內指引）、KDIGO、心房顫動、GINA、台灣高血壓指引，各取明確的避免事項 |
| 治療指引裡的「治療順序」 | 高血壓的第一線用藥、氣喘的階梯治療、血壓與血糖的控制目標 | 不適合：要知道病史、控制情形與檢驗值，單張處方判斷不了，做了多半是誤報 | 不做規則；適應症的解釋（哪個診斷可以解釋哪個藥）可以參考 |
| 給付規定 | 健保藥品給付規定 | 不是安全性問題，但不符規定會被核刪 | **待決定**：要不要另做一類「給付提醒」 |

幾個具體的判斷：

- **JNC**：JNC 8 是 2014 年的版本，之後沒有再更新；美國的高血壓指引改由 ACC/AHA 發布（2017 年版，2025 年 8 月改版）。國內以 2022 年台灣高血壓治療指引為準。所以清單列的是台灣高血壓治療指引與 AHA/ACC 2025，不列 JNC。高血壓指引的內容多半是治療順序與血壓目標，能做成規則的避免事項（ACEI 併用 ARB、β 阻斷劑併用 diltiazem／verapamil）已經由仿單與 EMA 的條文涵蓋，預期新增的規則很少。
- **GINA**：每年改版。能做成規則的只有少數明確的事項：氣喘診斷下開長效 β2 促效劑單方、卻沒有吸入性類固醇；氣喘配非選擇性 β 阻斷劑。GINA 不再建議只用短效 β2 促效劑治療，但這要看病人有沒有另外的控制型藥物，單張處方看不出來，不做。
- **GOLD**：明確的避免事項很少，先列為僅供查證。
- **STOPP/START 的 START**（應開而未開，例如心房顫動沒有抗凝血劑）：同一病人的其他處方看不到，容易誤報，不做規則。
- 依據等級維持現在的寫法（仿單、指引、常見、常見仿單外）。準則的建議強度與證據等級沒有另外記；需要時寫在審核頁的說明裡。

「建議加入」是起草者的評估，**加不加由藥師決定**：同意的話把狀態改成「使用中」。每週檢查從加入之日起，會照「使用中」與「建議加入」的來源找可能的漏報，依據來自「建議加入」的來源時標「待藥師判斷」。

## 欄位

| 欄位 | 說明 |
|---|---|
| 編號 | `S`＋兩位數。`S90` 是藥師的決定，不是外部來源 |
| 名稱、發布單位 | |
| 目前版本、版本日期 | 規則依據的版本。逐則公告的來源寫「逐則公告」 |
| 更新頻率 | 來源自己多久改版一次（說明用） |
| 確認週期月 | 幾個月去看一次有沒有新版或新通報；空白表示不用確認 |
| 上次確認 | `YYYY-MM-DD`：上次有人實際上網查過的日期。空白表示從未確認，版本是依起草者的知識填的 |
| 狀態 | `使用中`（已有規則引用，或資料表正在用）、`建議加入`、`待決定`、`僅供查證`、`不採用` |
| 用途 | 用在哪些規則、取哪一部分 |
| 引用寫法 | 規則的「依據」欄寫到它時用的字樣，多種以 `\|` 分隔。含版本（`Beers 2023`）時，寫別的版本的規則會被 `npm test` 擋下 |
| 網址、備註 | 備註記查證到的程度與下次要留意的事 |

## 怎麼維持最新

1. **每月確認**：每月第一個週一，每週審閱的排程工作（「GTsloth 處方樣本每週審閱」）做完每週檢查後，接著依 [`../rx-sources-review.md`](../rx-sources-review.md) 執行 `npm run rx-sources`，逐一上網查到期的來源（從未確認，或已滿確認週期），在 Drive 的「每週檢查」寫「指引確認_日期（審閱）」，需要決定的事寫成「指引確認_日期（提案）」，出現在審核頁的提案裡。它不改 repo。
2. **藥師團隊表決**提案：換不換版、哪些規則要跟著改、要不要加入新的來源。
3. **更新清單與規則**：負責人請 Claude 依表決結果改 `rx-sources.csv`（版本、上次確認、狀態）與規則表，照 `rx-rules.md` 的「修改流程」處理。
4. **換版時**：把清單的「目前版本」與「引用寫法」改成新版（例如 `Beers 2026`）以後，`npm test` 會列出每一條還寫著舊版的注意事項；逐條對照新版核對後，再把那一條的依據欄改成新版。沒核對的條文就留著舊寫法、留著失敗的測試，不要整批取代文字。
5. **每週檢查**也讀這份清單（`../rx-samples-weekly-review.md` 第 6 步），用來找規則沒抓到的問題。

`npm run rx-sources -- --date 2027-03-01` 可以看某一天有哪些來源到期。

## 還沒做的

- 仿單的逐條核對：每月確認每次核對 5 條「待核對」的條文，慢慢補齊。接入食藥署「全部藥品許可證資料集」的適應症與仿單原文是 `rx-rules.md`「後續工作」的項目。
- `indications.csv` 的依據欄只寫類別（仿單、指引、常見、常見仿單外），沒有寫是哪一份指引；之後可以在備註欄補上清單的編號。
- 清單上「上次確認」空白的來源，版本是依起草者的知識填的，第一次每月確認會補上。
